Testing & Môi trường triển khai

Alpha, staging và production khác nhau ra sao; các loại kiểm thử hay hỏi (white-box, black-box, smoke, regression, e2e) và bộ công cụ Playwright, Cucumber, Appium.

1 Quy trình phát hành

Alpha testing là gì?

Alpha thường là môi trường nội bộ, dùng để chạy alpha testing — giai đoạn kiểm thử đầu tiên sau khi tích hợp, dành cho đội phát triển và QA nội bộ.

  • Người test: developer và QA trong công ty, chưa mở cho người dùng thật.
  • Dữ liệu: dùng dữ liệu giả lập hoặc “dummy” để test ban đầu, không phải dữ liệu thật.
  • Mục tiêu: bắt lỗi tích hợp giữa các module ngay sau khi ghép, trước khi tốn công dựng môi trường giống production.
2 Quy trình phát hành

Staging khác production ở đâu?

Đáp án

Staging là bản sao gần như hoàn toàn giống môi trường production, dùng để test toàn hệ thống trước khi đưa lên live. Cấu hình, môi trường, dữ liệu… giống production nhất có thể; dữ liệu có thể là dữ liệu sản xuất đã được làm ẩn danh.

Staging là “bước cuối cùng” trước production, dùng để đảm bảo mọi thứ vận hành đúng như mong muốn trong môi trường như thật — khác với alpha là môi trường nội bộ với dữ liệu giả lập.

3 Kiểm thử

End-to-End (e2e) test kiểm tra cái gì?

E2E là phương pháp kiểm thử luồng hoạt động của ứng dụng từ đầu đến cuối, mô phỏng kịch bản của người dùng thực để xác nhận hệ thống và các thành phần của nó tích hợp đúng và dữ liệu toàn vẹn.

  • Giúp xác định sự phụ thuộc lẫn nhau giữa các thành phần của ứng dụng.
  • Đảm bảo thông tin được truyền giữa các thành phần hệ thống khác nhau là chính xác.

"Unit test chỉ đảm bảo từng hàm chạy đúng khi tách riêng, còn e2e chạy đúng kịch bản người dùng thật xuyên qua tất cả các tầng — FE, API, DB, cả email/thông báo — nên nó bắt được loại lỗi mà unit test không thấy: sai hợp đồng dữ liệu giữa hai service, thiếu bước trong luồng nghiệp vụ. Đổi lại e2e chạy chậm và dễ flaky nên em chỉ viết e2e cho các luồng quan trọng như đăng nhập và thanh toán, phần còn lại để unit và integration test lo."

4 React Native & Libs

Appium

  • is an open-source project and ecosystem of related software, designed to facilitate UI automation of many app platforms, including mobile (iOS, Android, Tizen), browser (Chrome, Firefox, Safari), desktop (macOS, Windows), TV (Roku, tvOS, Android TV, Samsung), and more!
  • Cho phép viết script tự động hóa bằng bất kỳ ngôn ngữ lập trình nào phổ biến (JS, Python, Java, Ruby, C#, v.v.) qua chuẩn giao tiếp WebDriver/W3C
  • Hoạt động theo mô hình Client–Server:
  • Appium hoạt động như một máy chủ HTTP (server), nhận các lệnh từ client bằng giao thức WebDriver (REST + JSON)
  • Appium client library ở phía người dùng đóng vai trò gửi các lệnh đến server từ ngôn ngữ bạn chọn và xử lý phản hồi
  • Drivers trong appium là các thành phần chịu trách nhiệm thực thi lệnh kiểm thử trên từng nền tảng như iOS (dùng XCUITest driver), Android (UiAutomator2, Espresso), Windows (WinAppDriver)
  • WebdriverIO là Client gọi WebDriver API, giao tiếp với Appium server
5 Automation test

Automation test

  • Là quy trình sử dụng các công cụ hoặc phần mềm để tự động thực hiện các bước kiểm thử phần mềm thay vì kiểm thử thủ công (manual test) do con người thực hiện.
  • Thay vì manual test thì họ sẽ viết hoặc sử dụng sẵn script test case tự động.
  • Lợi ích :
  • Chạy test hàng trăm/lần chỉ mất vài phút thay vì nhiều giờ.
  • Dễ tích hợp CI/CD để auto run các script khi build code mới.
  • Dùng lại script cho các lần regression test.
  • Hạn chế :
  • Khi UI hoặc logic thay đổi, phải cập nhật test script.
  • Không phù hợp với test ngắn hạn , vì manual test sẽ nhanh hơn
  • Các tools: Selenium, Playwright, Cypress, …
6 Automation test

White-box testing

  • là 1 phương pháp kiểm thử đòi hỏi tester biết rõ cấu trúc bên trong, mã nguồn
  • Kiểm tra luồng logic, cấu trúc code, điều kiện rẽ nhánh, …
  • thực hiện unit test với các tools : JUnit , NUnit
7 Automation test

Black-box testing

  • là 1 phương pháp kiểm thử đòi hỏi tester chỉ tập trung vào đầu vào và đầu ra của hệ thống so với yêu cầu, ko cần quan tâm cấu trúc bên trong của phần mềm
  • tester cần hiểu yêu cầu, nghiệp vụ là đủ
8 Automation test

Smoke test

là một loại kiểm thử phần mềm nhanh và cơ bản nhằm xác minh rằng các chức năng chính và quan trọng nhất của hệ thống hoặc bản build mới có hoạt động hay không trước khi thực hiện các kiểm thử chi tiết hơn.

9 Automation test

Regression test

là quá trình kiểm thử phần mềm nhằm đảm bảo rằng những tính năng vốn đang hoạt động trước đây vẫn hoạt động bình thường sau khi hệ thống được thay đổi (ví dụ: fix bug, thêm tính năng mới, nâng cấp phiên bản).

10 Automation test

Environment testing

  • Quy trình các môi trường kiểm thử trong 1 dự án phần mềm:
  • Development: Dành cho developer phát triển các tính năng và test nhanh
  • UAT: Cho người dùng hoặc khách hàng kiểm tra và xác nhận tính năng, dữ liệu test mô phỏng thực tế
  • Staging (Pre-production): là bản sao gần như hoàn toàn giống môi trường production, dùng để test toàn hệ thống trước khi đưa vào live và có cấu hình, dữ liệu và server giống hệt production.
  • Production: Môi trường thật nơi end user sử dụng.

12 Automation test

Page object model

  • là một mẫu thiết kế (design pattern) thường được dùng trong automation testing
  • Mỗi trang (Page) hoặc thành phần lớn (Component) của ứng dụng sẽ được đại diện bởi một class trong code.- Class này chỉ chứa thông tin và thao tác liên quan đến trang đó, không chứa logic test.- Code test sẽ gọi các method từ những class này để thực hiện các hành động.
13 Automation test

Verification and validation testing

1. verification: kiểm tra đúng theo yêu cầu thiết kế, cụ thể là + ví dụ:

  • Kiểm tra tài liệu yêu cầu: Có đầy đủ chức năng “Tìm chuyến bay”, “Thanh toán”, “Gửi email xác nhận”.
  • Review thiết kế giao diện: Có đúng màu, đúng logo, đúng layout như bản vẽ không.- Review code: Các API gọi đúng tham số, trả đúng định dạng JSON như tài liệu.=> Không cần chạy ứng dụng, chỉ cần xem tài liệu, thiết kế, code → nếu đúng, nghĩa là Verification pass.

2. validation: kiểm tra đáp ứng nhu cầu người dùng, cụ thể là + ví dụ:

  • Mở app, tìm vé Hà Nội → TP.HCM ngày mai, hệ thống hiển thị kết quả chính xác.- Thanh toán thành công và nhận được email xác nhận.
  • Người dùng thực sự sử dụng được app để đặt vé như mong muốn.=> Cần chạy ứng dụng, nhập dữ liệu thật, thao tác như người dùng → nếu đúng, nghĩa là Validation pass.
14 Automation test

Playwright

  • Là một thư viện kiểm thử tự động (automation testing) mã nguồn mở do Microsoft phát triển, dùng để test UI của web app theo hướng E2E
  • Kiểm tra xem web hoạt động đúng trên nhiều trình duyệt: Chromium (Chrome/Edge), Firefox, WebKit (Safari).
  • Các ưu điểm:
  • Đa trình duyệt
  • Đa nền tảng
  • Hỗ trợ nhiều ngôn ngữ lập trình
  • Hỗ trợ test song song để tiết kiệm time
  • Core Features & Test Runner API:

  • Là cách để xác nhận kết quả test đúng với mong đợi thông qua expect()

15 Automation test

Cucumber

  • Là một công cụ kiểm thử tự động (automation testing tool)
  • Dùng để viết script test case bằng ngôn ngữ tự nhiên (Gherkin) , do đó hỗ trợ Behavior-Driven Development (BDD)
  • Giúp mô tả kịch bản test dễ đọc, dễ hiểu cho BA/QA/Dev
  • Dùng Gherkin syntax để viết kịch bản test:
  • Given: trạng thái ban đầu (bối cảnh).
  • When: hành động thực hiện.
  • Then: kết quả mong đợi.
