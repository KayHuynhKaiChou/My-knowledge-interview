Interview prep · Bài toán hệ thống

Case studies thực chiến

Sáu bài toán kinh điển được hỏi dưới dạng tình huống: flash sale, trừ tiền lũy đẳng, import/export file triệu dòng, chống spam OTP, bảng xếp hạng và đăng xuất mọi thiết bị.

1 SQL

1. Mua hàng Flash Sale / Đặt vé (Xử lý Race Condition)

Tình huống: Giả sử hệ thống chỉ còn đúng 1 vé xem phim hoặc 1 đôi giày giới hạn. Có 1000 người cùng bấm "Mua" vào cùng 1 mili-giây.

  • Cách xử lý thông thường (Dễ gây lỗi): Query kiểm tra số lượng tồn kho, nếu lớn hơn 0 thì thực hiện cập nhật trừ đi 1. Kết quả là cả 1000 request đều đọc được số lượng là 1 và hệ thống bán ra 1000 đôi giày, dẫn đến tình trạng "âm kho".
  • Cách xử lý tối ưu (Best Practice):
  • Sử dụng Database Lock: Áp dụng Pessimistic Lock (Khóa bi quan: SELECT ... FOR UPDATE để khóa dòng dữ liệu, người này xử lý xong người kia mới được vào) hoặc Optimistic Lock (Khóa lạc quan: thêm trường version vào bảng, update chỉ thành công nếu version khớp).
  • Sử dụng Redis (Khuyên dùng): Đưa số lượng tồn kho lên Redis. Sử dụng lệnh DECR (giảm số) vì Redis chạy đơn luồng (Single-thread), đảm bảo tuyệt đối không bao giờ bị trừ lố, đồng thời tốc độ cực nhanh so với thao tác trực tiếp trên Database.
2 SQL

2. Thanh toán / Trừ tiền (Tính Lũy Đẳng - Idempotency)

Tình huống: Người dùng bấm nút "Thanh toán", nhưng do mạng chậm nên họ bấm thêm 2-3 lần nữa. Hoặc khi hệ thống gọi API sang cổng thanh toán (Momo/VNPay) bị timeout và tự động gọi lại (Retry). Vấn đề là làm sao để khách hàng không bị trừ tiền nhiều lần.

  • Cách xử lý thông thường: Cứ có request đến là tạo giao dịch và gọi lệnh trừ tiền.
  • Cách xử lý tối ưu (Best Practice):
  • Thiết kế API theo chuẩn Idempotency (Tính lũy đẳng - thực hiện 1 lần hay 100 lần thì kết quả vẫn không thay đổi).
  • Yêu cầu Frontend gửi kèm một mã Idempotency-Key (thường là UUID sinh ra lúc render màn hình thanh toán) trên Header của API.
  • Backend nhận được key này sẽ lưu vào Redis hoặc Database. Nếu request thứ 2 bay tới mang cùng Key, hệ thống phát hiện ra đây là request lặp và trả về kết quả của lần 1, bỏ qua bước trừ tiền.
3 SQL

3. Import / Export file Excel, CSV hàng triệu dòng (Memory Management)

Tình huống: Hệ thống yêu cầu người dùng upload file danh sách khách hàng có 1 triệu dòng, hoặc tính năng xuất báo cáo giao dịch trong 5 năm của công ty.

  • Cách xử lý thông thường: Đọc toàn bộ nội dung file vào biến trong RAM để xử lý, hoặc query toàn bộ dữ liệu từ Database rồi ghi ra file. Việc này sẽ gây ra lỗi OOM (Out Of Memory), làm sập toàn bộ server.
  • Cách xử lý tối ưu (Best Practice):
  • Sử dụng Stream: Xử lý dữ liệu theo dạng dòng chảy (chunk). Đọc lên 1000 dòng, lưu vào Database, giải phóng RAM, rồi mới đọc tiếp 1000 dòng tiếp theo.
  • Xử lý bất đồng bộ (Background Job): Không bắt người dùng đứng đợi API phản hồi file. Trả về ngay thông báo: "Hệ thống đang xử lý, sẽ gửi thông báo sau". Sau đó đẩy tác vụ này vào Message Queue (RabbitMQ / BullMQ / Kafka) để các Worker xử lý ngầm. Khi hoàn tất, thông báo cho người dùng qua WebSocket hoặc Email.
4 SQL

4. Gửi mã OTP / Login (Chống Spam & Rate Limiting)

Tình huống: Kẻ gian sử dụng tool tự động gọi API /send-otp hàng trăm ngàn lần vào một số điện thoại, khiến công ty thiệt hại nặng chi phí SMS hoặc dùng tool để dò tìm mật khẩu (Brute Force).

  • Cách xử lý thông thường: Người dùng gọi API bao nhiêu lần thì hệ thống gửi đi bấy nhiêu tin nhắn.
  • Cách xử lý tối ưu (Best Practice):
  • Áp dụng Rate Limiting ở tầng API Gateway (Nginx/Kong) hoặc dùng Redis để đếm số lượng request.
  • Sử dụng các thuật toán chuẩn như Token Bucket hoặc Sliding Window.
  • Thiết lập giới hạn đa tầng: Ví dụ 1 IP tối đa 5 request/giây; 1 Số điện thoại tối đa nhận 3 SMS/ngày. Nếu vượt ngưỡng sẽ chặn (ban) IP đó tạm thời.
5 SQL

5. Danh sách sản phẩm Hot / Bảng xếp hạng (Caching nâng cao)

Tình huống: Trang chủ cần hiển thị Top 10 sản phẩm bán chạy nhất. Để giảm tải Database, dữ liệu này được lưu vào Redis (Cache) với thời gian hết hạn (TTL) là 1 tiếng. Vấn đề phát sinh khi đúng khoảnh khắc Cache hết hạn, có 10.000 người dùng đang truy cập trang chủ cùng lúc.

  • Cách xử lý thông thường: Khi thấy Cache không có dữ liệu, hệ thống cho phép cả 10.000 request chọc thẳng vào Database để tính toán lại Top 10. Việc này làm CPU Database nhảy lên 100% và sập hệ thống (Lỗi này gọi là Cache Stampede hay Cache Breakdown).
  • Cách xử lý tối ưu (Best Practice):
  • Sử dụng Mutex Lock (Khóa phân tán) trên Redis. Khi Cache hết hạn, chỉ cho phép duy nhất 1 request đi thẳng vào Database để tính toán và cập nhật lại Cache. 9999 request còn lại phải đứng đợi vài mili-giây, khi có Cache mới thì lấy ra trả về luôn.
  • Tránh hiện tượng Cache Avalanche (Hàng loạt Cache hết hạn cùng lúc) bằng cách cộng thêm một khoảng thời gian ngẫu nhiên vào TTL (Ví dụ: 60 phút + random từ 1 đến 5 phút).
6 SQL

6. Tính năng Đăng xuất mọi thiết bị (Quản lý JWT)

Tình huống: Hầu hết các hệ thống hiện nay dùng JWT (JSON Web Token) vì đặc tính "Stateless" (Không cần lưu session trong Database). Tuy nhiên, nhược điểm chí mạng của JWT là Backend không thể thu hồi nó trước khi nó tự hết hạn. Vậy làm sao để xử lý chức năng "Đăng xuất khỏi thiết bị khác" hoặc "Khóa tài khoản khẩn cấp"?

  • Cách xử lý tối ưu (Best Practice):
  • Thiết lập JWT (Access Token) có thời hạn rất ngắn (ví dụ: 15 phút), kết hợp với Refresh Token lưu ở Database có thời hạn dài (ví dụ: 7 ngày).
  • Sử dụng cơ chế Blacklist (Danh sách đen) lưu trên Redis: Khi người dùng bấm đăng xuất hoặc đổi mật khẩu, đưa JWT đó (hoặc id của JWT) vào danh sách Blacklist trên Redis. Mọi request sử dụng token trong danh sách này đều bị Middleware từ chối ngay lập tức.
  • Cách thay thế (Token Versioning): Lưu một trường token_version (số nguyên) trong bảng User. Trong payload của JWT cũng chứa mã version này. Cứ mỗi lần thực hiện Force Logout, hệ thống tăng số token_version trong Database lên 1. Middleware sẽ kiểm tra version trong token, nếu thấp hơn version trong Database thì từ chối truy cập.
