"Redis là gì, dùng trong những case study thực tế nào của dự án?"

7.1 — Redis là gì

Redis là in-memory database — dữ liệu được lưu trực tiếp trong RAM thay vì ổ đĩa như DB truyền thống (MySQL, PostgreSQL) — nên đọc/ghi nhanh hơn rất nhiều lần (dưới 1ms so với 5-20ms của DB đọc từ ổ đĩa). Đánh đổi lại: RAM có giới hạn dung lượng và đắt hơn ổ đĩa nhiều, nên Redis không dùng để thay thế hoàn toàn DB chính — nó đóng vai trò là lớp tăng tốc / lưu trữ tạm thời phía trên 1 nguồn dữ liệu gốc.

Redis không chỉ lưu "thông tin tạm" theo nghĩa hẹp

Nhiều người mới học nghĩ Redis chỉ hợp với dữ liệu ngắn hạn (OTP, session). Thực tế Redis còn được dùng để cache lại chính dữ liệu đã có trong DB (profile user, thông tin sản phẩm...) — không phải vì bản thân dữ liệu đó có tính tạm thời, mà vì mục đích là đọc nhanh hơn, giảm tải cho DB chính. DB vẫn luôn là "nguồn sự thật" (source of truth); Redis chỉ giữ 1 bản sao, có thể mất đi bất cứ lúc nào (restart, hết TTL, bị evict do hết RAM) mà hệ thống vẫn hoạt động bình thường — chỉ chậm hơn tạm thời vì phải query lại DB. Đây chính là tiêu chí để phân biệt "cái gì nên để trong Redis" và "cái gì bắt buộc phải nằm trong DB": nếu mất dữ liệu đó mà hệ thống vẫn chạy được (chỉ chậm hơn), nó hợp để cache; nếu mất là hỏng luôn nghiệp vụ, nó phải nằm trong DB.

7.3 — Cache lại record DB: vì sao cần, và cách tránh "lệch" giữa Redis và DB

Cache (Redis) và Database là 2 hệ thống lưu trữ tách biệt, không tự động đồng bộ với nhau — update DB xong, Redis không tự biết để cập nhật theo, trừ khi code chủ động làm việc đó. Đây là nguồn gốc của "lệch" (cache inconsistency).

Bước 1: DB có name = "Nguyen Van A", Redis cache cũng "Nguyen Van A" (khớp nhau)

Bước 2: User đổi tên → UPDATE DB SET name = 'Nguyen Van B'
        → DB đã đúng, NHƯNG code QUÊN cập nhật/xoá Redis cache

Bước 3: Request khác đọc profile → check cache trước → cache VẪN "Nguyen Van A"
        → trả về dữ liệu CŨ dù DB đã có dữ liệu MỚI  → ĐÂY LÀ "LỆCH"

Ngay cả khi code làm đúng (update DB xong thì xoá cache ngay), vẫn có khoảng lệch tạm thời rất ngắn giữa lúc DB commit xong và lúc cache được xoá theo — vì 2 thao tác này không xảy ra trong cùng 1 tích tắc:

t=5ms:    UPDATE DB xong → DB đã đúng
t=5.05ms: Request KHÁC đọc cache đúng lúc này → cache CHƯA kịp xoá → trả dữ liệu cũ
t=6ms:    Code xoá cache xong → từ giờ cache mới đúng trở lại
Vì sao không dùng cache để check số dư trước khi trừ tiền (nhắc lại mục 6.5)

DB thật đã còn 2 triệu sau khi trừ, nhưng nếu cache chưa kịp cập nhật vẫn hiển thị 10 triệu — 1 request khác dựa vào cache để quyết định "còn đủ tiền cho phép rút thêm" sẽ dẫn tới rút vượt quá số dư thực có. Đây là lý do cache chỉ nên dùng để hiển thị, không dùng làm căn cứ cho quyết định nghiệp vụ quan trọng — quyết định đó luôn phải đọc trực tiếp từ DB với đúng lock.

7.4 — Tổng quan các cấu trúc dữ liệu chính trong Redis

Redis không chỉ là "key-value đơn giản" — nó hỗ trợ nhiều kiểu cấu trúc dữ liệu khác nhau, mỗi loại có đặc tính riêng phù hợp cho từng bài toán.

1. String — đơn giản nhất, lưu 1 giá trị

SET user:123:name "Nguyen Van A"
GET user:123:name → "Nguyen Van A"

INCR page_views:article_5    → tăng bộ đếm lên 1

Dùng khi: giá trị đơn giản, chỉ cần đọc/ghi nguyên khối — cache 1 record (dạng JSON string), session token, OTP, bộ đếm đơn giản (INCR), rate limit fixed window (mục 5.2), idempotency key (Câu 2), distributed lock (SET key value NX EX, mục 1.6).

2. Hash — giống 1 object có nhiều field, gọn hơn String riêng lẻ

HSET user:123 name "Nguyen Van A" age 30 city "HCM"
HGET user:123 name → "Nguyen Van A"
HGETALL user:123 → { name: "...", age: 30, city: "..." }

Dùng khi: dữ liệu có nhiều field liên quan tới nhau, muốn đọc/sửa từng field riêng lẻ mà không cần đọc/ghi lại toàn bộ object — ví dụ Token Bucket (mục 5.4, chỉ cần 2 field tokens và lastRefill), cache 1 record có cấu trúc (thay vì lưu cả record dưới dạng 1 chuỗi JSON string rồi phải parse lại mỗi lần đọc).

3. List — danh sách có thứ tự, thêm/lấy ở 2 đầu

LPUSH job_queue "job_abc123"     → thêm job vào đầu danh sách
RPOP job_queue                    → lấy job ra từ cuối danh sách (FIFO)

Dùng khi: cần hàng đợi đơn giản (queue nhẹ, Câu 10) — worker liên tục BRPOP (blocking pop) để lấy job xử lý dần. Khác Kafka/SQS ở chỗ List đơn giản hơn nhiều, không có partition, không đảm bảo bền vững cao — chỉ phù hợp job không quá quan trọng (không phải thanh toán).

4. Set — tập hợp không trùng lặp, không có thứ tự

SADD user:123:favorites "product_1" "product_2"
SISMEMBER user:123:favorites "product_1" → true (kiểm tra có tồn tại không)
SINTER user:123:favorites user:456:favorites → giao của 2 tập hợp

Dùng khi: cần kiểm tra "có tồn tại chưa" cực nhanh, hoặc tính toán tập hợp (giao/hợp/hiệu) — ví dụ: danh sách sản phẩm yêu thích, tag của bài viết, kiểm tra user đã đọc bài viết X chưa (tránh đếm view trùng), tìm bạn chung giữa 2 user.

5. Sorted Set (ZSET) — giống Set nhưng mỗi phần tử có thêm 1 "điểm số" để tự sắp xếp

ZADD leaderboard 1500 "player_A"
ZADD leaderboard 2300 "player_B"
ZREVRANGE leaderboard 0 9 WITHSCORES   → lấy top 10 điểm cao nhất
ZSCORE leaderboard "player_A" → 1500

Dùng khi: cần dữ liệu luôn được sắp xếp theo 1 tiêu chí số (điểm số, thời gian, giá...) và truy vấn theo khoảng — đây chính là cấu trúc dùng cho Sliding Window Log (mục 5.3, dùng timestamp làm score để lọc theo khoảng thời gian), leaderboard/bảng xếp hạng (điểm số game, top sản phẩm bán chạy), hoặc feed tin tức sắp xếp theo thời gian đăng.

6. Pub/Sub — kênh phát-nhận tin nhắn real-time, không lưu trữ

// Service A (publisher)
PUBLISH notifications:user_123 "Bạn có đơn hàng mới"

// Service B (subscriber) — đang lắng nghe kênh này
SUBSCRIBE notifications:user_123
→ nhận ngay lập tức: "Bạn có đơn hàng mới"

Dùng khi: cần gửi thông báo tức thời giữa các service hoặc tới client đang kết nối (qua WebSocket) — ví dụ chat real-time đơn giản, thông báo đẩy khi có đơn hàng mới, đồng bộ trạng thái giữa nhiều instance backend (ví dụ khi 1 instance update cache, publish để các instance khác biết mà invalidate cache local của chúng).

Điểm khác biệt quan trọng: Pub/Sub không lưu trữ gì cả

Nếu không có ai đang SUBSCRIBE vào đúng lúc message được publish, message đó mất luôn vĩnh viễn, không giống List hay Streams (bên dưới) là dữ liệu vẫn nằm đó chờ được lấy ra. Vì vậy Pub/Sub không phù hợp cho job quan trọng (không thể dùng cho thanh toán) — chỉ hợp với thông báo real-time mà mất 1-2 cái cũng không sao (ví dụ 1 chat message bị mất do subscriber vừa mất kết nối, người dùng có thể gửi lại).

7. Redis Streams — giống Kafka thu nhỏ, có lưu trữ + ack

XADD orders_stream * order_id 123 amount 500000
XREADGROUP GROUP workers consumer1 COUNT 1 STREAMS orders_stream >
→ worker nhận được message, xử lý xong thì XACK để đánh dấu đã xử lý

Dùng khi: cần queue có độ tin cậy cao hơn List/Pub-Sub — có lưu trữ lại lịch sử message, hỗ trợ nhiều consumer group, hỗ trợ cơ chế ack giống Kafka (message chưa ack sẽ được giao lại) — đúng tinh thần "at-least-once delivery" đã nói ở mục 4.4. Đây là lựa chọn khi muốn dùng Redis làm message queue "nghiêm túc" hơn thay vì chỉ dùng List đơn giản.

Trả lời mẫu khi phỏng vấn

"Em chọn cấu trúc dựa trên hình dạng dữ liệu và cách mình cần truy vấn nó — cần sắp xếp theo điểm số thì Sorted Set, cần object nhiều field sửa riêng lẻ thì Hash, cần kiểm tra tồn tại/tính giao-hợp thì Set, cần hàng đợi đơn giản thì List, còn cần độ tin cậy cao hơn cho queue thì em cân nhắc Streams thay vì List thường."

7.5 — 3 chiến lược ghi cache phổ biến

Chiến lượcCách hoạt độngRủi ro / phù hợp khi
Write-throughGhi DB xong ghi luôn cache trong cùng flow (đồng bộ)Cache luôn mới nhưng chậm hơn 1 chút vì thêm bước ghi cache
Write-behindGhi cache trước, DB ghi bất đồng bộ sauNhanh nhưng rủi ro mất dữ liệu nếu cache crash trước khi flush — không phù hợp cho dữ liệu tiền
Cache-aside (phổ biến nhất)Đọc: check cache trước, miss thì đọc DB rồi set cache. Ghi: update DB rồi invalidate (xoá) cacheKhông update cache trực tiếp để tránh out-of-order write

Race condition ở cache-aside

2 request cùng cache-miss → cả 2 cùng đọc DB → cả 2 cùng set cache — nếu 1 trong 2 đọc dữ liệu cũ hơn, cache cuối cùng có thể là data cũ (ai set sau thắng, không nhất thiết mới nhất). Giảm thiểu bằng cách set cache kèm timestamp/version (chỉ ghi đè nếu mới hơn), hoặc dùng mutex ngắn khi cache-miss để chỉ 1 request đi đọc DB.

Trả lời mẫu khi phỏng vấn

"Redis em dùng cho nhiều mục đích trong dự án: cache lại dữ liệu hay đọc để giảm tải DB, lưu session/OTP, làm rate limiter, làm queue nhẹ cho background job, distributed lock khi cần khoá xuyên nhiều instance, và idempotency key để chống xử lý trùng. Với riêng việc cache lại dữ liệu từ DB, em dùng chiến lược cache-aside — đọc thì check cache trước miss mới query DB, ghi thì update DB rồi xoá cache thay vì update cache trực tiếp — và luôn đặt TTL dự phòng để nếu có bug quên xoá cache, dữ liệu cũ cũng tự hết hạn sau 1 khoảng thời gian, không lệch mãi mãi."
