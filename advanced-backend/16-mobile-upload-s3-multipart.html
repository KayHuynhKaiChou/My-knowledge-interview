Flow Mobile upload file nặng lên S3 thông qua BE ở ZCC

Bước 1 — Gọi API /initiate

- Mobile gọi API này để báo "tôi sắp upload 1 file ghi âm", kèm theo thông tin mime type của file (ví dụ audio/mp4, audio/x-wav...) và tổng số chunk sẽ gửi. BE dựa vào mime type để biết đây là loại file gì (audio hay file nén), từ đó xác định đuôi file để tạo 1 key cho obj file sắp đc upload. Vd: key: 'recordings/abc.mp3'

- BE khởi tạo 1 phiên upload dạng multipart trên S3. Phiên upload S3 cần có key mới tạo . Sau đó lưu lại thông tin phiên (session) upload S3 vào Redis, và trả về 1 uploadId để dùng cho các bước tiếp theo.

- Còn gửi tổng số chunk để BE dùng ở bước 2

Bước 2 — Gọi API /chunks nhiều lần

- Mobile chia file thành nhiều phần nhỏ (chunk), gửi lần lượt từng chunk kèm uploadId và số thứ tự chunk lên BE. Cụ thể là gọi api /chunks/2 (2 là số thứ tự part) và body là nội dung nhị phân của file chunk.

- BE sẽ dùng total chunks ở bước 1 để check part number bên mobile gửi đúng ko , ví dụ total chunk là 5 mà gửi 7 là reject luôn. Bên cạnh đó tính % tiến độ để hiển thị cho người dùng. Cụ thể là % đã upload = số chunk đã nhận / tổng số chunk rồi response về cho mobile hiển thị

- BE gửi chunk đó + part number + uploadId lên S3 (theo cơ chế upload từng "part" của multipart upload). Part number là số thứ tự của mỗi chunk file để S3 có thể ghép đúng các chunk đảm bảo thứ tự

- S3 nhận xong sẽ sinh ra 1 ETag cho part đó và trả về cho BE.
BE lưu ETag này + part number vào Redis (trong session upload đang chạy).
Các chunk tiếp theo cũng làm y hệt. Cứ như vậy cho đến khi đủ số chunk đã khai báo ở bước /initiate.

Bước 3 — Gọi API /complete

- Mobile báo "đã gửi xong hết chunk". BE kiểm tra lại xem đã đủ ETag cho tất cả các chunk theo đúng thứ tự chưa (nếu thiếu chunk nào thì báo lỗi ngay, không cho ghép).

- Nếu đủ, BE gửi danh sách ETag kèm số thứ tự part đó lên S3, yêu cầu S3 ghép các part lại thành 1 file hoàn chỉnh. S3 dùng chính các ETag này để xác thực đúng part, đúng thứ tự từng part (chunk), rồi ghép lại thành 1 obj file và lưu vào bucket với key đã tạo ở /initiate.

- Sau khi ghép xong, BE mới tạo bản ghi (record) trong database để lưu key tạo ở bước 1, rồi mới đẩy job xử lý AI vào hàng đợi như đã nói ở phần trước.
