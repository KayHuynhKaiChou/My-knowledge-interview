14 Câu hỏi ứng dụng thường gặp

"Import Excel nhiều dòng để insert/upsert — FE và BE cần làm gì để tối ưu?"

14.1 — Vấn đề gốc: file nhiều dòng không nên xử lý đồng bộ trong 1 request

File Excel càng nhiều dòng, thời gian đọc + validate + insert càng lâu — nếu xử lý ngay trong 1 request HTTP, client phải chờ, dễ timeout, và giữ chiếm connection/tài nguyên server suốt thời gian đó (đúng vấn đề đã học ở mục 4.1). Nguyên tắc: import file luôn nên xử lý bất đồng bộ, áp dụng lại đúng tinh thần Background Job (Câu 10) và Queue (Câu 4).

14.2 — Kiến trúc tổng thể FE-BE: Upload → Background Job → Validate toàn bộ → Chia chunk insert/upsert → Polling tiến độ → Báo cáo kết quả

React (FE)                    NestJS (BE)
    │                              │
    │  1. Upload file              │
    ├─────────────────────────────►│  Lưu file tạm, đẩy job vào QUEUE
    │  ◄── 202 Accepted, jobId ─────┤  (không xử lý ngay trong request)

Vì sao phải validate xong TOÀN BỘ rồi mới chia chunk, không validate xen kẽ theo từng chunk

Nếu để mỗi chunk tự validate và tự query DB check trùng riêng, sẽ có 2 vấn đề: (1) N+1 query — 5 chunk thì 5 lần query check trùng thay vì gộp 1 lần (mục 6.4); (2) không phát hiện được trùng lặp giữa các chunk khác nhau — ví dụ tên "A" xuất hiện ở cả chunk 1 và chunk 3, nếu mỗi chunk tự check riêng lẻ (transaction độc lập, không biết gì về chunk khác), chunk chạy sau sẽ âm thầm ghi đè lên chunk chạy trước qua upsert mà không có cảnh báo gì. Validate toàn bộ trước — bao gồm cả bước dò trùng ngay trong chính file — giải quyết dứt điểm cả 2 vấn đề trước khi bắt đầu ghi bất kỳ dòng nào vào DB.

BE — Controller nhận file, đẩy job, trả về ngay

@Controller('imports')
export class ImportController {
  constructor(@InjectQueue('excel-import') private importQueue: Queue) {}

  @Post('products')
  @UseInterceptors(FileInterceptor('file'))
  async uploadFile(@UploadedFile() file: Express.Multer.File) {
    const filePath = await this.storageService.saveTemp(file);
    const job = await this.importQueue.add('process-import', { filePath });
    return { jobId: job.id, status: 'processing' }; // trả ngay lập tức
  }

  @Get('products/:jobId/status')
  async getStatus(@Param('jobId') jobId: string) {
    const job = await this.importQueue.getJob(jobId);
    return { jobId, state: await job.getState(), progress: job.progress(), result: job.returnvalue };
  }
}

14.3 — Tối ưu xử lý ở BE: validate toàn bộ trước, rồi mới chia chunk để ghi

4 kỹ thuật quan trọng để 700 dòng hay 100.000 dòng đều xử lý mượt và không dính trùng lặp ngầm:

  • Đọc file theo Stream thay vì load hết vào RAM 1 lần (ExcelJS.stream.xlsx.WorkbookReader) — tránh tốn bộ nhớ khi file lớn.
  • Check trùng NGAY TRONG FILE trước — 2 dòng cùng tên trong chính file Excel phải được phát hiện, không để chúng lọt qua chunk khác nhau rồi âm thầm ghi đè lên nhau.
  • Gộp check trùng với DB thành 1 câu query duy nhất (WHERE name IN (...)), chạy 1 lần cho toàn bộ file — tránh N+1 (mục 6.4).
  • Chỉ sau khi có đầy đủ danh sách dòng hợp lệ, mới chia chunk để ghi — mỗi chunk bọc transaction riêng, chạy tuần tự, độc lập với nhau (không cần đọc lại dữ liệu chunk trước, vì mọi thứ cần biết đã được xác định xong ở bước validate).
@Process('process-import')
async handleImport(job: Job<{ filePath: string }>) {
  // ===== BƯỚC A: ĐỌC + VALIDATE TOÀN BỘ FILE TRƯỚC =====
  const reader = new ExcelJS.stream.xlsx.WorkbookReader(job.data.filePath, {});
  const rawRows = [];
  for await (const worksheet of reader) {
    for await (const row of worksheet) {
      if (row.number === 1) continue;
      rawRows.push({ name: row.getCell(1).value, price: row.getCell(2).value, rowNumber: row.number });
    }
  }

  const errors = [];

  // A1. Validate FORMAT từng dòng
  const formatValidRows = rawRows.filter(row => {
    if (!row.name || typeof row.price !== 'number' || row.price <= 0) {
      errors.push({ row: row.rowNumber, message: 'Dữ liệu không hợp lệ' });
      return false;
    }
    return true;
  });

  // A2. Check TRÙNG NGAY TRONG FILE — tránh trùng giữa các chunk khác nhau âm thầm ghi đè
  const seenInFile = new Map();
  const dedupedRows = [];
  for (const row of formatValidRows) {
    if (seenInFile.has(row.name)) {
      errors.push({ row: row.rowNumber, message: `Trùng với dòng ${seenInFile.get(row.name)} trong file` });
      continue;
    }
    seenInFile.set(row.name, row.rowNumber);
    dedupedRows.push(row);
  }

  // A3. Check TRÙNG VỚI DB — 1 CÂU QUERY DUY NHẤT cho toàn bộ file
  const existing = await this.productRepo.find({ where: { name: In(dedupedRows.map(r => r.name)) } });
  const existingMap = new Map(existing.map(p => [p.name, p]));
  // (existingMap dùng để phân biệt insert mới hay update — không phải để loại bỏ,
  //  vì đây là bảng cho phép upsert theo đúng nghiệp vụ)

  // ===== BƯỚC B: CHỈ SAU KHI VALIDATE XONG HẾT, MỚI CHIA CHUNK ĐỂ GHI =====
  const chunkSize = 200;
  let successCount = 0;

  for (let i = 0; i < dedupedRows.length; i += chunkSize) {
    const chunk = dedupedRows.slice(i, i + chunkSize);

    // Mỗi chunk 1 transaction ĐỘC LẬP — không đọc lại dữ liệu chunk trước,
    // vì mọi thứ cần biết (hợp lệ hay không, trùng hay không) đã xác định XONG ở Bước A
    await this.dataSource.transaction(async (manager) => {
      for (const row of chunk) {
        await manager.upsert(Product, { name: row.name, price: row.price }, ['name']);
      }
    });

    successCount += chunk.length;
    await job.progress(Math.min(Math.round(((i + chunkSize) / dedupedRows.length) * 100), 100));
  }

  return { total: rawRows.length, success: successCount, failed: errors.length, errors };
}
Concurrency Limiter — nếu muốn tăng tốc bằng chạy chunk song song

Ở trên các chunk chạy tuần tự (an toàn, đơn giản). Nếu file cực lớn (hàng trăm nghìn dòng) và cần nhanh hơn, có thể cho nhiều chunk chạy song song — nhưng phải giới hạn số lượng chạy cùng lúc, nếu không sẽ tràn connection pool DB (mục 1.6) khi có quá nhiều transaction mở cùng lúc. Concurrency Limiter là cơ chế giới hạn này — giống 1 "cổng soát vé" chỉ cho tối đa N tác vụ chạy cùng lúc, tác vụ thứ N+1 phải đợi tới khi 1 trong N tác vụ đang chạy xong.

import pLimit from 'p-limit';
const limit = pLimit(5); // tối đa 5 chunk chạy song song cùng lúc

const promises = chunks.map(chunk => limit(() => processChunk(chunk)));
await Promise.all(promises); // dù có 20 chunk, luôn chỉ 5 cái chạy cùng lúc

Điều kiện bắt buộc để chạy song song an toàn: các chunk chạy cùng lúc không được đụng vào cùng 1 record — nhờ bước check trùng nội bộ file đã làm ở Bước A, mỗi name chỉ xuất hiện đúng 1 lần trong toàn bộ dedupedRows, nên chia chunk kiểu gì cũng đảm bảo không có 2 chunk nào cùng đụng vào 1 record — an toàn để chạy song song nếu muốn.

14.4 — Validate: FE làm gì, BE làm gì — 3 loại validate

Nguyên tắc chung: validate cả 2 phía, nhưng vai trò khác nhau — FE để phản hồi nhanh (UX), BE luôn là nguồn xác nhận cuối cùng vì validate ở FE hoàn toàn có thể bị bypass (gọi thẳng API bằng Postman, sửa code JS) — đúng nguyên tắc "không tin dữ liệu đầu vào" đã áp dụng xuyên suốt (Câu 11, Câu 13).

Loại validateVí dụFE làm được khôngBE bắt buộc?

Vì sao check "unique với DB" tuyệt đối không thể để FE tự làm

FE không có cách nào biết chắc "mã này đã tồn tại chưa" mà không hỏi ngược BE — và ngay cả khi FE gọi API hỏi trước, vẫn có khả năng race condition giữa lúc hỏi xong và lúc thực sự submit (y hệt bài toán race condition ở Câu 1, chỉ khác ngữ cảnh "check tồn tại" thay vì "check số dư"). Check unique chỉ đáng tin khi BE tự làm ngay tại thời điểm insert/upsert.

Luồng thực tế: file → parse → preview → validate nhanh ở FE → submit → validate đầy đủ ở BE

FE:
1. User chọn file → FE đọc file NGAY TẠI TRÌNH DUYỆT (thư viện SheetJS/xlsx),
   CHƯA upload lên server → hiển thị PREVIEW bảng dữ liệu cho user xem trước
2. FE chạy validate NHANH loại 1 (rỗng, sai định dạng) trên dữ liệu preview
   → tô đỏ ngay ô lỗi, KHÔNG cần gọi API — phản hồi tức thì
3. User sửa lỗi hiển thị → bấm "Import" → LÚC NÀY mới upload file lên BE

BE:
4. Validate lại TOÀN BỘ từ đầu (không tin dữ liệu FE đã "sạch"):
   loại 1 (rỗng/format) → loại 2 (business rule) → loại 3 (unique với DB, gộp 1 query)
5. Trả về lỗi theo từng dòng, kèm số dòng trong Excel gốc để user dễ đối chiếu
Bài học: message lỗi giữa FE và BE phải khớp nhau

Nếu rule/message validate ở FE và BE không khớp nhau, user gặp tình huống form "pass" ở FE nhưng bị BE từ chối với thông báo khác hẳn — gây khó hiểu và mất niềm tin. Nên định nghĩa rule validate dùng chung cho cả 2 phía (ví dụ 1 schema Zod/Yup dùng được cả FE lẫn BE nếu cùng viết TypeScript), tránh tình trạng FE nói "hợp lệ" nhưng BE lại từ chối vì lý do không giống những gì FE đã kiểm tra.

Trả lời mẫu khi phỏng vấn

"Với file Excel nhiều dòng, em không xử lý đồng bộ trong request — đẩy vào background job, trả 202 ngay, FE poll tiến độ tương tự bài toán queue ở Câu 4. Ở BE em đọc file theo stream để tránh tốn RAM, gộp check trùng thành 1 câu query IN thay vì N+1, và upsert theo chunk có transaction riêng để lỗi 1 chunk không ảnh hưởng chunk khác. Về validate, em chia theo 3 loại: format cơ bản làm cả FE lẫn BE để UX nhanh, business rule nhiều cột bắt buộc BE enforce lại, còn check unique với DB thì chỉ có thể và chỉ nên làm ở BE vì FE không có quyền truy cập DB và dễ dính race condition nếu cố check trước ở phía client."
