5 Câu hỏi ứng dụng thường gặp

"Làm sao chặn 1 user spam request rút tiền/đặt hàng liên tục?"

5.1 — Rate Limiting là gì

Mục tiêu: giới hạn 1 user/IP chỉ được gọi API tối đa N lần trong 1 khoảng thời gian (ví dụ tối đa 10 request/giây). Nếu không giới hạn, 1 user (cố ý spam hoặc bug ở client tự động retry vô hạn) có thể gửi hàng nghìn request/giây, làm sập DB hoặc chiếm hết tài nguyên của người dùng khác. Vấn đề kỹ thuật cần giải: làm sao đếm được "user này đã gọi bao nhiêu lần trong khoảng thời gian gần đây" một cách chính xác và nhanh — đó là lý do cần thuật toán riêng, không chỉ đơn giản là 1 biến đếm.

5.2 — Fixed Window Counter: chia thời gian thành khung cố định theo lịch

Chia thời gian thành các khung cố định, đóng theo lịch (giống chia lịch theo tháng — tháng nào cũng bắt đầu từ ngày 1), không phụ thuộc request tới lúc nào. Redis lưu từng khung riêng biệt — mỗi khung là 1 key chứa số lượng request đã đếm được trong khung đó — chứ không phải 1 key duy nhất bị reset giá trị về 0.

Làm sao biết request thuộc khung nào

Máy tính quy đổi thời gian thành Unix timestamp (số giây kể từ 1/1/1970), rồi xác định khung bằng phép chia lấy nguyên (floor — chia xong bỏ phần thập phân):

window_size = 60 giây (kích thước mỗi khung)
window_id = floor(unix_timestamp / window_size)

Con số window_id đại diện chính xác cho 1 khung 60 giây cụ thể. Bất kỳ request nào rơi vào cùng khoảng 60 giây đó đều tính ra cùng 1 window_id, vì phép chia nguyên bo tất cả các giây trong khoảng về chung 1 khung:

9:52:00 → timestamp 1750000320 → floor(1750000320/60) = 29166672  → cùng khung
9:52:44 → timestamp 1750000364 → floor(1750000364/60) = 29166672  → cùng khung
9:52:59 → timestamp 1750000379 → floor(1750000379/60) = 29166672  → cùng khung
9:53:00 → timestamp 1750000380 → floor(1750000380/60) = 29166673  → KHUNG MỚI (khác số)

Redis lưu gì cho Fixed Window — key theo window_id, kèm TTL để tự thay khung mới

Mỗi khung 60 giây tương ứng với 1 key Redis riêng biệt, có vòng đời độc lập — không phải 1 key bị "reset về 0". Khi khung hết hạn, key cũ tự bị Redis xoá (qua TTL), và khung mới bắt đầu bằng 1 key hoàn toàn mới, độc lập với key cũ.

const windowSize = 60; // giây

function checkRateLimit(userId) {
  const now = Math.floor(Date.now() / 1000);         // unix timestamp hiện tại (giây)
  const windowId = Math.floor(now / windowSize);       // tính khung — CÔNG THỨC Ở TRÊN

  const key = `rate_limit:${userId}:${windowId}`;
  // ví dụ key thực tế: "rate_limit:user_123:29166672"

  const count = redis.incr(key);   // tăng bộ đếm của key này lên 1 (chưa có thì tự tạo = 1)

  if (count === 1) {
    redis.expire(key, windowSize); // lần đầu của khung này → đặt TTL = 60s để tự xoá
  }

  if (count > 5) {
    return { allowed: false };     // vượt quá 5 → từ chối (count vẫn giữ nguyên, KHÔNG lùi lại 0)
  }
  return { allowed: true };
}

Ví dụ minh hoạ (không cần đổi ra Unix timestamp để dễ hình dung, dù thực tế vẫn phải quy đổi như công thức ở trên): giới hạn 5 request / 60 giây. 1 request gửi lúc 10:10:20 — hệ thống xác định khung 60 giây chứa mốc này là [10:10:00 → 10:11:00] (khung cố định theo lịch tròn phút, không tính lùi từ thời điểm request). Redis lưu 1 key đại diện cho đúng khung này, đặt TTL để key tự hết hạn khi khung kết thúc (còn khoảng 40 giây nữa tính từ 10:10:20, vì khung kết thúc lúc 10:11:00), kèm theo 1 bộ đếm bắt đầu từ 0.

Nếu bộ đếm hiện tại < 5 thì request được cho phép và bộ đếm tăng thêm 1. Mọi request khác cũng rơi vào cùng khung [10:10:00 → 10:11:00] — ví dụ lúc 10:10:35, 10:10:50 — đều dùng chung đúng 1 key, 1 bộ đếm đó, cứ tăng dần cho tới khi chạm 5 thì các request tiếp theo trong khung này bị từ chối (429), bộ đếm vẫn giữ nguyên chứ không lùi lại. Khi đồng hồ chạm mốc 10:11:00, key này tự hết hạn (Redis tự xoá) — request đầu tiên rơi vào khung mới [10:11:00 → 10:12:00] sẽ tạo ra 1 key hoàn toàn mới, bộ đếm lại bắt đầu từ 0.

Add / xoá diễn ra khi nào

Add (tăng): mỗi khi có request tới, INCR ngay trên key của khung hiện tại — không có bước "thêm" riêng, INCR tự tạo key nếu chưa có. Xoá: không xoá bằng tay — dùng EXPIRE key 60 đặt ngay tại lần đầu tiên key được tạo, để Redis tự động xoá key đó sau đúng 60 giây. Khi khung mới bắt đầu (window_id khác), 1 key hoàn toàn mới được sinh ra, độc lập với key cũ — key cũ tự "chết" theo TTL riêng, không ai cần chủ động dọn.

Lỗ hổng kinh điển của Fixed Window

10:00:56 → 10:00:59 → user dồn gọi 5 request LIÊN TIẾP, đếm 1→5,
                       tất cả CHO PHÉP vì cùng thuộc Khung [10:00:00-10:01:00)
10:01:01 → SANG KHUNG MỚI → đếm reset về 0 (key mới)
           → user LẠI dồn gọi tiếp 5 request nữa ngay 10:01:01-10:01:04
              đều CHO PHÉP vì thuộc khung mới, đếm mới toanh

→ KẾT QUẢ: user gọi được 10 request chỉ trong vòng 8 giây,
   dù quy định là "5 request / 60 giây" — vượt xa ý định giới hạn ban đầu!

Đây chính là lý do sinh ra Sliding Window — để xoá bỏ lỗ hổng ở đúng ranh giới giữa 2 khung.

5.3 — Sliding Window Log: đếm chính xác trong "cửa sổ thời gian trượt"

Đếm số request đã xảy ra trong N giây gần nhất, tính từ chính thời điểm request hiện tại — không cố định theo mốc phút/giây tròn. Mỗi request mới đến, cửa sổ được tính lại hoàn toàn mới: luôn là "N giây ngược về trước tính từ thời điểm request đó", không nối tiếp từ mốc cũ.

Ví dụ minh hoạ: giới hạn 5 request / 60 giây. Redis đang lưu 1 mảng rỗng [] cho user này. Request đầu tiên gửi vào lúc 10:10:20 — lấy 10:10:20 làm mốc kết thúc (end time), lùi lại 60 giây để lấy mốc bắt đầu (start time) là 10:09:20. Vậy khung đang xét là [10:09:20 → 10:10:20].

Từng phần tử timestamp đang có trong mảng sẽ được kiểm tra: cái nào thuộc khung [10:09:20 → 10:10:20] thì giữ lại, cái nào không thuộc (cũ hơn 10:09:20) thì bị xoá khỏi mảng. Sau khi lọc xong, lấy độ dài mảng (số phần tử còn lại) so sánh với 5 — nếu ≥ 5 thì trả về 429 (từ chối), nếu < 5 thì cho phép và thêm timestamp 10:10:20 vào mảng. Vì đây là request đầu tiên nên mảng đang rỗng, độ dài = 0 < 5 → cho phép, mảng giờ thành [10:10:20]. Request tiếp theo đến lúc nào cũng lặp lại đúng quy trình này — tự tính lại khung riêng của nó, không dùng chung khung cố định với request trước.

Vì sao gọi là "trượt" (sliding): khác với fixed window (cửa sổ cố định theo lịch: [0-60s), [60-120s)..., dễ bị spam dồn ở 2 đầu ranh giới khung mà vẫn "hợp lệ" theo từng khung riêng lẻ), sliding window luôn tính lùi đúng N giây từ chính thời điểm hiện tại — không có lỗ hổng ranh giới này.

Khác biệt cốt lõi giữa 2 cách xác định mốc khung

Sliding Window: mốc bắt đầu khung tính lùi lại từ chính thời điểm request (10:10:20 → lùi 60s → 10:09:20) — mỗi request có 1 khung riêng của nó, khung này "trượt" theo sát thời gian thực.

Fixed Window: mốc khung cố định theo lịch tròn phút (10:10:00 → 10:11:00), không quan tâm request rơi vào giây nào trong phút đó — nhiều request khác nhau (10:10:05, 10:10:20, 10:10:55...) đều dùng chung 1 khung, 1 key, 1 bộ đếm duy nhất cho tới khi phút đó kết thúc.

Redis lưu gì cho Sliding Window Log

Redis lưu timestamp của từng request đã xảy ra, dùng cấu trúc Sorted Set (ZSET) — vì ZSET cho phép sắp xếp và lọc theo khoảng giá trị (dùng timestamp làm điểm sắp xếp — "score").

const key = `rate_limit:sliding:${userId}`;
const now = Date.now();
const windowMs = 60000; // cửa sổ 60 giây

// Bước 1: xoá các timestamp đã "trượt" ra khỏi cửa sổ (cũ hơn 60s so với hiện tại)
await redis.zremrangebyscore(key, 0, now - windowMs);

// Bước 2: đếm số request còn lại trong cửa sổ
const count = await redis.zcard(key);

if (count >= 10) {
  throw new Error("429 Too Many Requests");
}

// Bước 3: ghi nhận request hiện tại — value phải DUY NHẤT (ZSET không cho trùng value)
// nên thường ghép thêm số random/uuid vào cùng timestamp
await redis.zadd(key, now, `${now}-${Math.random()}`);
await redis.expire(key, 60); // tự dọn key nếu user ngừng gọi hẳn

Mỗi request thành công tạo ra 1 entry riêng trong ZSET — nếu user gọi 10 request/giây liên tục, ZSET đó chứa hàng trăm entry timestamp. Đây chính là lý do Sliding Window Log tốn bộ nhớ hơn Token Bucket: nó lưu lại "dấu vết" của từng request, kích thước dữ liệu tăng theo số lượng request.

Tóm gọn khác biệt cách Redis lưu: Fixed Window vs Sliding Window

Fixed Window: Redis lưu từng khung riêng biệt — mỗi khung là 1 key (định danh bằng window_id) chứa số lượng request đã đếm trong khung đó (kiểu dữ liệu số nguyên, dùng INCR); khung hết hạn (TTL) thì key tự biến mất, khung mới sinh ra key hoàn toàn mới.

Sliding Window Log: Redis lưu 1 danh sách (mảng) các timestamp của từng request đã xảy ra (dùng ZSET); không có khái niệm "khung" hay "reset" — mỗi request cũ tự "rơi rụng" dần khỏi danh sách khi quá 60 giây tuổi, còn request mới liên tục được thêm vào.

5.4 — Token Bucket: cái xô chứa token, refill dần theo thời gian

Mỗi user có 1 cái xô (bucket) chứa tối đa N token. Mỗi lần user gọi API, hệ thống lấy đi 1 token trong xô — hết token thì từ chối request (429). Xô này tự động được đổ thêm token dần dần theo thời gian (ví dụ mỗi giây thêm 2 token, tới khi đầy).

Xô của user A: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙]  10 token đầy

User A gọi 10 request liên tiếp trong 1 giây → dùng hết 10 token
Xô của user A: [ ]  0 token → request thứ 11 bị từ chối

1 giây sau, xô tự refill thêm 2 token (quy định "refill 2 token/giây")
Xô của user A: [🪙🪙]  → user lại được gọi thêm 2 request nữa

Điểm khác biệt cốt lõi so với Sliding Window: Token Bucket cho phép burst — user được gọi dồn dập 1 lúc (miễn còn token trong xô), nhưng về lâu dài trung bình vẫn bị giới hạn theo tốc độ refill. Giống việc được phép tiêu hết tiền tiết kiệm trong 1 ngày, nhưng lương chỉ về từ từ mỗi tháng.

Redis lưu gì cho Token Bucket

Khác hẳn Sliding Window Log, Token Bucket không lưu từng request — chỉ cần lưu đúng 2 con số cho mỗi user: số token còn lại trong xô, và thời điểm lần cuối xô được refill (để tính xem đã tới lúc thêm token mới chưa). Dùng cấu trúc Hash trong Redis.

const key = `rate_limit:bucket:${userId}`;
const maxTokens = 10;
const refillRate = 2; // 2 token mỗi giây
const now = Date.now();

// Đọc trạng thái xô hiện tại (Redis Hash lưu 2 field: tokens và lastRefill)
let bucket = await redis.hgetall(key);

if (!bucket || Object.keys(bucket).length === 0) {
  bucket = { tokens: maxTokens, lastRefill: now };   // lần đầu → xô đầy
} else {
  // Tính từ lần refill trước tới giờ đã được thêm bao nhiêu token
  const elapsedSeconds = (now - bucket.lastRefill) / 1000;
  const tokensToAdd = elapsedSeconds * refillRate;
  bucket.tokens = Math.min(maxTokens, bucket.tokens + tokensToAdd);
  bucket.lastRefill = now;
}

if (bucket.tokens < 1) {
  throw new Error("429 Too Many Requests"); // hết token, không có gì để trừ
}

bucket.tokens -= 1; // trừ 1 token cho request này
await redis.hset(key, { tokens: bucket.tokens, lastRefill: bucket.lastRefill });
await redis.expire(key, 3600); // dọn key nếu user ngừng hoạt động lâu

Redis chỉ giữ 1 record duy nhất cho mỗi user (2 field: tokens, lastRefill), bất kể user đó đã gọi bao nhiêu request trong quá khứ — kích thước dữ liệu cố định, không phình to theo lưu lượng như Sliding Window Log.

5.5 — Rate limit ở API Gateway hay ở Service?

"Chặn thô" ở Gateway nghĩa là kiểm tra đơn giản, không cần biết gì về business logic bên trong — chỉ dựa vào thông tin có sẵn ngay ở tầng network/HTTP (IP, user_id trong token, path của API). Gateway đứng trước tất cả service, không biết (và không cần biết) chi tiết nghiệp vụ như "user này có phải VIP không" — chỉ đếm request theo IP/user, vượt ngưỡng thì chặn ngay, không cho đi tiếp vào hệ thống phía sau. Mục đích chính là chặn spam/DDoS quy mô lớn sớm nhất có thể, giống bảo vệ đứng ở cổng chỉ kiểm tra thẻ ra vào, không kiểm tra bạn định làm gì bên trong toà nhà.

Request → [API Gateway: check thô — IP này gọi > 100 req/phút chưa? Có → chặn ngay]
              ↓ (nếu chưa vượt ngưỡng)
          [Order Service: check tinh — user này có đang có 1 đơn pending chưa
           thanh toán không? Loại sản phẩm này có giới hạn mua mỗi user không?]

"Chặn tinh" ở Service là chặn dựa theo logic nghiệp vụ cụ thể của từng chức năng (business rule, không phải chỉ đếm request đơn thuần) — ví dụ "user này đã đặt hàng sản phẩm X quá 3 lần trong ngày rồi". Gateway giảm tải sớm cho toàn hệ thống nhưng khó áp rule theo business logic; Service linh hoạt hơn nhưng request đã tốn tài nguyên đi qua Gateway trước khi bị chặn. Thực tế: dùng cả 2 lớp.
