11 Câu hỏi ứng dụng thường gặp

"Multi-tenant là gì, khi nào cần dùng, thiết kế sao cho đúng?"

11.1 — Multi-tenant là gì

Multi-tenant (đa khách thuê) là mô hình kiến trúc trong đó 1 hệ thống phần mềm duy nhất phục vụ nhiều khách hàng (tenant) khác nhau, mỗi khách hàng có dữ liệu riêng, cấu hình riêng, nhưng đều dùng chung 1 codebase, 1 hạ tầng triển khai — thay vì phải dựng riêng 1 bản cài đặt (instance) hoàn toàn tách biệt cho mỗi khách hàng.

Đây chính là mô hình đứng sau hầu hết các sản phẩm SaaS (Software as a Service) — ví dụ Slack, Shopify, hay 1 hệ thống quản lý nhân sự bán cho nhiều công ty khác nhau: mỗi công ty là 1 "tenant", đăng nhập vào cùng 1 hệ thống nhưng chỉ nhìn thấy dữ liệu của chính công ty mình, hoàn toàn không thấy được dữ liệu của công ty khác.

11.2 — Khi nào cần dùng multi-tenant

  • Xây dựng sản phẩm SaaS bán cho nhiều khách hàng doanh nghiệp (B2B) — mỗi khách hàng là 1 tổ chức riêng biệt, cần cách ly dữ liệu rõ ràng.
  • Muốn tiết kiệm chi phí vận hành — quản lý 1 hệ thống chung dễ hơn nhiều so với dựng và bảo trì hàng trăm bản cài đặt riêng lẻ cho từng khách hàng.
  • Cần deploy tính năng mới đồng loạt cho mọi khách hàng cùng lúc, thay vì phải cập nhật thủ công từng instance riêng.
  • Không nên dùng multi-tenant nếu khách hàng yêu cầu cách ly tuyệt đối ở tầng hạ tầng vật lý (ví dụ ngành ngân hàng, y tế có quy định pháp lý bắt buộc dữ liệu phải nằm trên hạ tầng riêng hoàn toàn) — lúc đó vẫn phải cân nhắc single-tenant (mỗi khách 1 instance riêng) dù tốn chi phí vận hành hơn.

11.3 — 3 mô hình kiến trúc multi-tenant phổ biến

Mô hìnhCách hoạt độngƯu điểmNhược điểm
Database per tenant
(Silo model)		 Mỗi tenant có 1 database riêng biệt hoàn toàn, cùng chung code ứng dụng Cách ly dữ liệu mạnh nhất, dễ backup/restore riêng từng khách, dễ đáp ứng yêu cầu compliance Tốn chi phí hạ tầng (N tenant = N database), khó quản lý migration đồng loạt (phải chạy trên từng DB)
Schema per tenant
(Bridge model)		 Chung 1 database, nhưng mỗi tenant có 1 schema riêng (PostgreSQL hỗ trợ tốt mô hình này) Cân bằng giữa cách ly và tiết kiệm chi phí — vẫn tách bảng riêng nhưng chung 1 connection pool, 1 server DB Vẫn giới hạn số lượng tenant tối đa 1 DB có thể chứa nổi (hàng nghìn schema có thể làm chậm DB), migration vẫn phải chạy trên từng schema
Shared database, shared schema
(Pool model)		 Tất cả tenant dùng chung 1 database, 1 schema, 1 bộ bảng — phân biệt dữ liệu bằng 1 cột tenant_id trên mỗi bảng Tiết kiệm chi phí nhất, dễ scale số lượng tenant lên rất lớn, migration chạy 1 lần cho tất cả Rủi ro cao nhất nếu code quên lọc tenant_id — dễ rò rỉ dữ liệu chéo giữa các tenant nếu lập trình viên sơ suất

11.4 — Ví dụ 1 dự án cụ thể: hệ thống giám sát nhân sự bán cho nhiều công ty

Giả sử xây dựng 1 sản phẩm SaaS theo dõi giờ làm việc, chấm công, năng suất nhân viên — bán cho nhiều công ty khách hàng khác nhau (công ty A, công ty B, công ty C...). Mỗi công ty là 1 tenant, có nhân viên riêng, báo cáo riêng, cấu hình quy tắc chấm công riêng (ví dụ công ty A tính giờ làm theo ca, công ty B tính theo giờ hành chính cố định).

Chọn mô hình Shared database + tenant_id (Pool model) vì số lượng khách hàng có thể lên tới hàng trăm, hàng nghìn công ty nhỏ — dựng riêng DB cho từng công ty sẽ quá tốn kém và khó vận hành:

-- Mọi bảng nghiệp vụ đều có thêm cột tenant_id
CREATE TABLE employees (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,   -- xác định thuộc công ty nào
  name VARCHAR(255),
  email VARCHAR(255)
);

CREATE TABLE attendance_logs (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  employee_id BIGINT,
  check_in_time TIMESTAMP,
  check_out_time TIMESTAMP
);

-- Composite index luôn đặt tenant_id làm cột đầu (xem lại mục 9.2)
CREATE INDEX idx_tenant_employee ON attendance_logs (tenant_id, employee_id, check_in_time);

Mọi query đều bắt buộc lọc theo tenant_id, không có ngoại lệ:

-- SAI — quên lọc tenant_id, sẽ trả về dữ liệu của TẤT CẢ công ty trộn lẫn
SELECT * FROM employees WHERE id = 105;
-- ĐÚNG — luôn kèm tenant_id trong mọi câu query
SELECT * FROM employees WHERE id = 105 AND tenant_id = 42;

Xác định tenant nào đang gọi request — resolve tenant_id ở đâu

Thường xác định tenant qua 1 trong các cách: subdomain riêng cho từng công ty (company-a.example.com), header riêng (X-Tenant-ID), hoặc lấy từ thông tin user đã đăng nhập (JWT payload có sẵn tenant_id). Cách phổ biến và an toàn nhất là lấy từ JWT sau khi xác thực — tránh để FE tự gửi tenant_id trong query param (dễ bị giả mạo, gửi sai tenant_id của công ty khác).

// NestJS — Guard hoặc Middleware trích tenant_id từ JWT đã xác thực
@Injectable()
export class TenantMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const payload = req['user']; // đã được set bởi JwtAuthGuard chạy trước đó
    req['tenantId'] = payload.tenantId; // gắn tenantId vào request, dùng xuyên suốt
    next();
  }
}

// employee.service.ts — LUÔN nhận tenantId, không bao giờ query thiếu điều kiện này
async findEmployeeById(tenantId: number, employeeId: number) {
  return this.employeeRepo.findOne({
    where: { id: employeeId, tenantId },   // bắt buộc luôn có tenantId trong where
  });
}
Rủi ro lớn nhất của Pool model — và cách phòng ngừa

Chỉ cần 1 chỗ trong code quên thêm điều kiện tenant_id, dữ liệu của công ty này có thể lộ sang công ty khác — hậu quả nghiêm trọng cho 1 SaaS B2B. Cách phòng ngừa thực tế: dùng Row-Level Security (RLS) của PostgreSQL để DB tự động lọc theo tenant_id ở tầng database, không phụ thuộc hoàn toàn vào việc lập trình viên nhớ thêm điều kiện ở tầng code; hoặc dùng 1 base repository/base query builder dùng chung, tự động inject tenant_id vào mọi query, tránh lặp lại thủ công dễ sót ở từng chỗ gọi.

11.5 — Nhược điểm của Multi-tenant

  • Rủi ro rò rỉ dữ liệu chéo giữa các tenant — nghiêm trọng nhất. Với Shared database (Pool model), chỉ cần 1 chỗ trong code quên lọc tenant_id, dữ liệu công ty A có thể lộ sang công ty B — lỗi bảo mật có thể dẫn tới mất hợp đồng, kiện tụng, mất uy tín hoàn toàn.
  • "Noisy neighbor" — 1 tenant dùng quá tải ảnh hưởng tenant khác. Vì nhiều tenant dùng chung hạ tầng (database, connection pool, CPU server — mục 1.6), nếu 1 tenant có traffic đột biến (chạy báo cáo nặng, bị tấn công DDoS), toàn bộ tenant khác dùng chung hệ thống đều bị chậm theo dù không liên quan gì tới sự cố đó.
  • Khó tuỳ biến sâu cho từng khách hàng riêng lẻ — thêm logic rẽ nhánh riêng cho 1 tenant lớn (nhiều if (tenantId === X) rải rác) làm code phức tạp dần theo thời gian, khó bảo trì lâu dài.
  • Migration/deploy rủi ro cao hơn — dùng chung 1 codebase và thường là 1 database, mỗi lần deploy hoặc chạy migration schema ảnh hưởng TẤT CẢ tenant cùng lúc; nếu migration có bug, mọi khách hàng đang dùng hệ thống đều gặp sự cố cùng lúc — khác với single-tenant có thể rollout dần theo từng khách (canary release).
  • Khó đáp ứng compliance/pháp lý nghiêm ngặt — 1 số ngành (ngân hàng, y tế, chính phủ) yêu cầu dữ liệu nằm trên hạ tầng vật lý tách biệt hoàn toàn, đôi khi phải ở khu vực địa lý cụ thể (data residency) — nhiều công ty SaaS phải làm riêng 1 "enterprise tier" chạy single-tenant chỉ để phục vụ nhóm khách hàng này.
  • Backup/restore riêng cho 1 tenant khó khăn (với Pool model) — nếu 1 khách hàng lỡ xoá nhầm dữ liệu và yêu cầu khôi phục về thời điểm trước đó, không thể restore riêng dữ liệu của 1 tenant mà không ảnh hưởng tenant khác, vì restore cả DB sẽ làm dữ liệu mọi tenant khác cũng quay về thời điểm cũ.
  • Query dễ chậm dần khi số lượng tenant và dữ liệu tăng lên — mọi tenant cùng đọc/ghi vào cùng 1 bảng vật lý, bảng càng lớn (gộp dữ liệu hàng nghìn tenant) càng cần tối ưu kỹ (composite index đúng thứ tự với tenant_id làm cột đầu — mục 9.2, hoặc partition theo tenant_id — mục 6.2).

Trả lời mẫu khi phỏng vấn

"Multi-tenant là kiến trúc 1 hệ thống phục vụ nhiều khách hàng khác nhau nhưng dùng chung codebase và hạ tầng, mỗi khách hàng là 1 tenant với dữ liệu tách biệt. Em chọn giữa 3 mô hình tuỳ quy mô: database riêng cho từng tenant nếu cần cách ly mạnh và số lượng khách ít, schema riêng nếu cần cân bằng, hoặc shared schema với cột tenant_id nếu cần scale số lượng tenant lớn và tiết kiệm chi phí. Nhược điểm lớn nhất của shared schema là rủi ro rò rỉ dữ liệu chéo nếu code quên lọc tenant_id, và noisy neighbor — 1 tenant dùng quá tải ảnh hưởng tenant khác vì dùng chung hạ tầng. Ngoài ra deploy hay migration cũng rủi ro hơn vì ảnh hưởng tất cả khách hàng cùng lúc, và khó đáp ứng compliance nghiêm ngặt đòi hỏi cách ly hạ tầng vật lý hoàn toàn — những trường hợp đó em vẫn phải cân nhắc single-tenant dù tốn chi phí vận hành hơn. Để giảm rủi ro rò rỉ dữ liệu, em luôn xác định tenant từ JWT đã xác thực và cân nhắc dùng Row-Level Security ở tầng DB làm lớp bảo vệ thứ 2."
