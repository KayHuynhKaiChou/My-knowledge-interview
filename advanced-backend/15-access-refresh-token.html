Access token & refresh token

15.1 — Flow handle access token và refresh token

Step 1: User login success ở 1 device => BE response về thông tin user này kèm 2 field là access token
và refresh token để lưu ở FE

Step 2: Intercaptor chặn ở trước lúc gửi req cho BE với logic là lấy access token đc lưu trong local storage/cookie và đính kèm vào request header
Authorization: Bearer token. Bên cạnh đó ở Intercaptor chặn ở trước lúc FE nhận response từ BE

Step 3: Nếu status của response là 401 thì sẽ gọi 1 api refresh token , api này nhận refresh token từ FE lưu ở cookie

Step 4: ở api refresh token , nếu refresh token còn hạn hoặc chưa bị revoke (tức revoked_at là null) thì return về 1 cặp token mới gồm access và refresh token.
Do đó ko dùng lại refresh token cũ nữa , cả FE và BE đều cập nhật

Step 5: chạy lại các api đã bị 401 trước đó với access token mới ở req header Authorization

15.2 — Logout ở 1 thiết bị và logout ở all thiết bị mà user đó đang đăng nhập theo phương pháp blacklist token

Cách thực hiện:

Step 1: User login ở 1 device thông qua api login

Step 2: BE sẽ sinh ra 1 cặp access token và refresh token , refresh token sẽ lưu ở DB tương ứng với device của user.
Còn payload của access token JWT sẽ lưu {id, role, ext, id_jwt}. Bên cạnh đó BE sẽ lưu {userId: 123, id_jwt: abc} vào redis với TTL bằng đúng TTL của access token. Lưu ý là ko chỉ login , cứ logic nào liên quan đến vc sinh ra access token mới.

Step 3: Khi click logout, gọi api logout
- Nếu 1 thiết bị: BE sẽ revoke refresh token của device đó
- Nếu nhiều thiết bị: BE sẽ revoke all refresh token thuộc về user này
=> nếu dừng lại ở revoke refresh token thì các phiên đăng nhập của user này vẫn còn vì access token chưa hết hạn,
do đó nếu muốn tự logout sau khi gửi 1 request private (cần authorization) sẽ cần step 4

Step 4: giả sử phiên đăng nhập của user trên device macbook , 1 request từ device macbook gửi tới BE . In the middleware , BE sẽ đọc header Authorization và decode jwt access token

Step5: sau khi encode xong , lấy đc id_jwt.
- Nếu 1 thiết bị: BE sẽ so sánh id_jwt từ macbook với id_jwt đc lưu ở redis với thời gian
- Nếu nhiều thiết bị: BE sẽ lấy các id_jwt của user đưa vào 1 list , list này ng ta gọi là blacklist token. sau đó sẽ check là id_jwt macbook này có nằm trong blacklist ko , nếu có thì trả status 401

15.3 — Logout ở 1 thiết bị và logout ở all thiết bị mà user đó đang đăng nhập theo phương pháp token version

Cách thực hiện:

Step 1: User login ở 1 device thông qua api login

Step 2: BE sẽ sinh ra 1 cặp access token và refresh token , refresh token sẽ lưu ở DB tương ứng với device của user. Sẽ có thêm 1 cột là token_version ở bản user và đồng thời nhúng luôn token_version hiện tại vào payload của JWT access token.

Step 3: Khi click logout trên 1 hay nhiều device , BE sẽ tăng token_version lên 1

Step 4: giả sử phiên đăng nhập của user trên device macbook , 1 request từ device macbook gửi tới BE . In the middleware , BE sẽ đọc header Authorization và decode jwt access token

Step 5: sau khi encode xong , lấy đc token_version. Dù 1 hay nhiều thiết bị thì sẽ đầu đi check token version đc lưu trong DB hiện tại có bằng token version đc lưu trong JWT hay ko ở middleware , nếu không bằng thì trả status 401

15.4 — Logout ở 1 thiết bị và logout ở all thiết bị mà user đó đang đăng nhập theo phương pháp token version nhưng cách làm khác

- Step tương tự , chỉ khác là thay vì sinh ra 1 cột token_version thì sẽ lưu thời gian user nhấn logout hay thời gian thực hiện revoke 1 hoặc nhiều refresh token lại ở redis theo user id.

- Giả sử phiên đăng nhập của user trên device macbook , 1 request từ device macbook gửi tới BE . In the middleware , BE sẽ đọc header Authorization và decode jwt access token. Lúc này sẽ lấy ngày tạo access token so sánh với revoked_at , nếu ngày tạo access token < revoked_at thì trả status 401
