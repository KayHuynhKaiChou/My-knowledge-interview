Advanced Backend / Câu 01
1 Câu hỏi ứng dụng thường gặp

"10 triệu trong tài khoản, 2 request cùng trừ 6 triệu — xử lý sao?"

Đây là câu hỏi nền tảng nhất khi phỏng vấn backend/payment. Nó test 3 lớp hiểu biết liền nhau: race condition là gì → 2 loại lock giải quyết ra sao → và rủi ro deadlock khi dùng lock sai cách.

1.1 — Vấn đề gốc: khoảng hở giữa đọc và ghi

Cách làm sai phổ biến nhất là đọc số dư ra ứng dụng, kiểm tra, rồi mới ghi lại — giữa 3 bước này có một khoảng hở (gap) mà request khác có thể chen vào.

Sai — có khoảng hở giữa đọc và ghi
const account = await db.query("SELECT balance FROM account WHERE id=1");
// A và B cùng đọc được balance = 10.000.000

if (account.balance >= 6000000) {   // cả 2 request đều pass điều kiện này
  await db.query(
    "UPDATE account SET balance = ? WHERE id=1",
    account.balance - 6000000        // cả 2 đều tính ra 4.000.000
  );
}
// Kết quả: balance cuối cùng = 4.000.000 (đáng lẽ phải là -2tr / báo lỗi)
// 1 trong 2 giao dịch coi như "biến mất" — mất tiền hoặc dư tiền sai
t=0ms
Request A: SELECT balance → đọc được 10.000.000
t=1ms
Request B: SELECT balance → CŨNG đọc được 10.000.000 (A chưa ghi gì cả)
t=2ms
Request A: UPDATE balance = 4.000.000
t=3ms
Request B: UPDATE balance = 4.000.000 (ghi đè, không biết gì về A)

1.2 — Cách giải đúng #1: Atomic UPDATE (khuyên dùng cho phép cộng/trừ đơn giản)

Gộp cả đọc, kiểm tra điều kiện và ghi vào một câu lệnh SQL duy nhất — để DB tự đảm bảo atomic ở tầng row, không cần lock tường minh.

Đúng — không có khoảng hở
UPDATE account
SET balance = balance - 6000000
WHERE id = 1 AND balance >= 6000000;

-- affected_rows == 1 → trừ thành công
-- affected_rows == 0 → không đủ tiền, reject

Điểm mấu chốt: balance - 6000000 là biểu thức tương đối, được DB tính toán ngay tại thời điểm UPDATE thực thi, dựa trên giá trị mới nhất trong DB — không phải giá trị đã đọc ra ứng dụng từ trước. Vì vậy không quan trọng 2 request cách nhau bao lâu (kể cả vài mili giây): DB luôn serialize 2 UPDATE cùng chạm 1 row bằng row-lock ngầm định, request đến sau sẽ chạy trên dữ liệu đã được request trước cập nhật xong.

Cẩn thận — lỗi tinh vi khi "tưởng" là atomic

Nếu vẫn đọc balance ra app rồi tính rồi SET balance = <giá trị tuyệt đối> (dù có kèm điều kiện WHERE giống hệt), vẫn bị lost update: điều kiện WHERE có thể vẫn đúng (vì check trên giá trị mới nhất) nhưng giá trị SET lại dựa trên dữ liệu cũ, ghi đè mất mọi thay đổi xảy ra ở giữa.

Trông giống atomic nhưng vẫn sai — SET giá trị tuyệt đối tính sẵn ở app
SELECT balance FROM account WHERE id = 1;  -- đọc được 10.000.000
-- tính ở app: 10tr - 6tr = 4tr
UPDATE account SET balance = 4000000 WHERE id = 1 AND balance >= 6000000;
t=0
Bạn SELECT → đọc được balance = 10.000.000
t=1
Giao dịch KHÁC cộng thêm 5.000.000 → balance thực tế lúc này là 15.000.000
t=2
UPDATE ... SET balance = 4000000 WHERE balance >= 6000000 → điều kiện vẫn ĐÚNG (15tr ≥ 6tr) → ghi đè thẳng 4.000.000 → khoản 5tr vừa cộng vào BỊ MẤT TRẮNG

Chỉ an toàn khi phép tính là biểu thức tương đối, được DB tính ngay trong câu SQL (balance = balance - 6000000) — không phải hard-code hay tính sẵn ở app rồi truyền số tuyệt đối xuống. Vấn đề không nằm ở chỗ "số đó hard-code hay tính toán", mà nằm ở chỗ phép trừ diễn ra ở đâu — ở app (dựa trên dữ liệu cũ, luôn rủi ro) hay ở DB (dựa trên dữ liệu mới nhất tại thời điểm ghi, an toàn).

1.3 — Cách giải đúng #2: Pessimistic Lock (khi phải tính toán phức tạp ở application)

Atomic UPDATE ở mục 1.2 chỉ viết được khi phép tính là biểu thức tương đối đơn giản mà SQL diễn đạt gọn trong 1 dòng (balance - 6000000). Nhưng nếu số tiền trừ phụ thuộc vào dữ liệu ở bảng khác — ví dụ phải trừ 6 triệu nhưng cộng lại một khoản voucher đang active của account đó — thì bắt buộc phải đọc dữ liệu ra application để tính toán trước, không thể nhét gọn vào 1 câu UPDATE như SET balance = balance - 6000000 + voucher_amount được, vì voucher_amount nằm ở bảng vouchers, không phải cột có sẵn trên bảng account.

Đây chính là lúc khoảng hở giữa đọc và ghi quay trở lại — và pessimistic lock được dùng để bịt khoảng hở đó trong lúc application xử lý logic phức tạp:

BEGIN;

-- Bước 1: lock row account NGAY KHI ĐỌC — request khác chạm vào row này
-- sẽ bị BLOCK ở đây cho tới khi transaction này COMMIT
SELECT balance FROM account WHERE id = 1 FOR UPDATE;   -- app nhận về balance = 10.000.000

-- Bước 2: TÍNH TOÁN Ở APPLICATION — đây là lý do cần lock
--   - query thêm bảng vouchers để lấy voucher đang active của account này
--   - áp dụng business rule (voucher tối đa bao nhiêu %, có hết hạn chưa...)
--   - có thể mất vài chục ms, thậm chí gọi thêm service khác
const voucher = await db.query(
  "SELECT amount FROM vouchers WHERE account_id = 1 AND status = 'active' FOR UPDATE"
);                                         // ví dụ voucher.amount = 500.000
const newBalance = 10000000 - 6000000 + voucher.amount;   // app tự tính = 4.500.000
await db.query(
  "UPDATE vouchers SET status = 'used' WHERE account_id = 1 AND status = 'active'"
);

-- Bước 3: ghi giá trị ĐÃ TÍNH XONG xuống — an toàn vì suốt từ bước 1
-- không có request nào khác chen được vào row này
UPDATE account SET balance = 4500000 WHERE id = 1;

COMMIT;   -- lúc này request khác đang đợi mới được đọc balance mới nhất

Nếu không có FOR UPDATE ở bước 1, một request B khác có thể đọc balance = 10.000.000 song song trong lúc A đang tính toán voucher, rồi B ghi đè lên kết quả của A ngay sau khi A COMMIT — y hệt bài toán lost update ở mục 1.2, chỉ khác là lần này khoảng hở nằm ở bước tính voucher chứ không phải phép trừ đơn thuần. FOR UPDATE giữ nguyên row bị khoá suốt từ lúc đọc cho tới lúc COMMIT, nên dù application có mất bao lâu để tính toán, không ai chen vào giữa được.

Vậy khi nào chọn atomic UPDATE (1.2), khi nào chọn pessimistic lock (1.3)?

Atomic UPDATE khi phép tính viết gọn được thành 1 biểu thức SQL thuần (chỉ dùng cột ngay trên chính bảng đó). Pessimistic lock khi phải đọc thêm dữ liệu từ bảng khác, gọi thêm logic/service, rồi mới tính ra được giá trị cuối cùng để ghi — lúc đó không thể tránh khỏi bước "đọc ra app rồi tính" nên phải khoá row lại trong suốt thời gian đó.

1.4 — Cách giải đúng #3: Optimistic Lock (dùng cột version)

-- Bước 1: đọc kèm version
SELECT balance, version FROM account WHERE id = 1;  -- balance=10tr, version=5

-- Bước 2: tính toán ở app (có thể phức tạp, tốn thời gian, gọi thêm service khác...)
newBalance = balance - 6000000

-- Bước 3: ghi, kèm điều kiện version phải khớp với lúc đọc
UPDATE account SET balance = newBalance, version = version + 1
WHERE id = 1 AND version = 5;

-- affected_rows == 0 → version đã đổi, có người update trước → đọc lại & RETRY

1.5 — Vì sao cần cột version riêng, không tận dụng luôn cột balance?

version và balance đều chỉ là column bình thường, không có gì đặc biệt về cơ chế DB — khác biệt nằm ở ý nghĩa: version là con số vô nghĩa về nghiệp vụ, chỉ để trả lời "row này có bị đổi gì không kể từ lúc tôi đọc" — bắt được mọi thay đổi trên row, bất kể đổi field nào. Còn balance là giá trị nghiệp vụ thật. Nếu dùng thẳng balance làm điều kiện chống conflict thay cho version, sẽ dính lại đúng lỗi lost update đã gặp ở mục 1.2 — chỉ khác là lần này có kèm điều kiện WHERE nhưng vẫn không đủ:

Dùng balance thay version — vẫn dính lost update
SELECT balance FROM account WHERE id = 1;  -- 10tr
-- tính toán ở app: 10tr - 6tr = 4tr
UPDATE account SET balance = 4000000 WHERE id = 1 AND balance >= 6000000;
t=0
Bạn SELECT → đọc được balance = 10tr
t=1
1 giao dịch KHÁC (ví dụ ai đó chuyển khoản vào) cộng thêm 5tr → balance thực tế bây giờ là 15tr
t=2
Bạn chạy UPDATE ... SET balance = 4000000 WHERE balance >= 6000000 → điều kiện balance >= 6000000 vẫn ĐÚNG (vì 15tr >= 6tr) → UPDATE thành công, balance bị SET THẲNG thành 4000000 → 5tr vừa được cộng vào LÚC NÃY BỊ MẤT TRẮNG!

Dùng chính balance làm điều kiện chỉ an toàn khi phép tính là cộng/trừ tương đối viết gọn trong 1 UPDATE, để DB tự tính ngay tại thời điểm ghi (mục 1.2: balance = balance - 6000000). Ngay khi logic phức tạp hơn — phải đọc ra app tính toán rồi mới ghi giá trị tuyệt đối xuống — dùng balance làm điều kiện sẽ không đủ, vì WHERE có thể pass (check đúng trên giá trị mới nhất) trong khi SET lại ghi đè lên thay đổi đã xảy ra ở giữa mà điều kiện đó không hề biết tới. Đây chính là lý do cần một cột riêng, vô can với nghiệp vụ, chỉ để phát hiện "có ai đụng vào row này chưa" — đó là vai trò của version.

1.6 — So sánh Pessimistic vs Optimistic Lock

3 thuật ngữ dùng trong bảng so sánh: Contention, Connection Pool và Throughput

Contention (tranh chấp) = mức độ nhiều request cùng muốn đụng vào chung 1 row tại cùng thời điểm. Contention cao nghĩa là rất nhiều request tranh nhau 1 row (ví dụ ví tiền của 1 KOL giờ cao điểm, hàng nghìn giao dịch/giây cùng chạm vào 1 account). Contention thấp nghĩa là hiếm khi có 2 request cùng chạm vào 1 row (ví dụ 1 admin và 1 user A cùng lúc sửa profile của user A, cả tháng chưa chắc có 2 request trùng nhau).

Connection Pool = một "hồ chứa" gồm sẵn N kết nối (connection) đã mở tới DB, dùng chung cho toàn bộ ứng dụng — vì mở 1 connection mới tới DB khá tốn thời gian (bắt tay TCP, xác thực...), nên hệ thống mở sẵn 1 số lượng cố định (ví dụ 100 connection), mỗi request cần nói chuyện với DB sẽ "mượn" 1 connection trong pool, dùng xong thì trả lại cho request khác dùng tiếp. Vì số lượng connection trong pool là có giới hạn, nếu tại 1 thời điểm có nhiều hơn 100 request cùng cần dùng DB, những request dư ra phải xếp hàng đợi có connection trống mới chạy được — bất kể request đó có liên quan gì tới row đang bị tranh chấp hay không.

Throughput = số lượng request mà hệ thống (DB) xử lý xong được trong 1 đơn vị thời gian (ví dụ số giao dịch/giây). Throughput không chỉ phụ thuộc vào 1 row đang được tranh chấp — nó còn phụ thuộc vào connection pool nói trên. Nếu pessimistic lock giữ 1 row quá lâu, request đang đợi lock đó vẫn tiếp tục giữ luôn 1 connection trong pool suốt thời gian chờ — dù bản thân nó chỉ cần vài mili giây để chạy nếu không phải đợi. Khi đủ nhiều request cùng đợi như vậy, connection pool có thể bị chiếm hết, khiến cả những request đến row hoàn toàn khác — vốn không liên quan gì tới tranh chấp — cũng bị nghẽn theo vì không còn connection trống để mượn. Đó là lý do throughput của toàn hệ thống giảm, chứ không chỉ riêng những request đang chạm vào row bị tranh chấp.

"Pessimistic lock chọn cách ngăn chặn trước, chấp nhận độ trễ để đảm bảo chắc chắn không conflict. Optimistic lock chọn cách phát hiện sau, không chặn ai cả, chỉ kiểm tra lúc ghi rồi retry nếu có tranh chấp. Em chọn pessimistic khi biết trước tranh chấp xảy ra thường xuyên và giữ lock lâu sẽ nghẽn connection pool — ví dụ ví tiền giờ cao điểm. Em chọn optimistic khi tranh chấp hiếm nhưng vẫn có thể xảy ra — ví dụ user mở app trên 2 thiết bị cùng sửa 1 profile — lúc đó không đáng để lock chờ cho một trường hợp hiếm khi xảy ra."

1.7 — Retry ở Optimistic Lock: làm sao và khi nào dừng

async function withdrawOptimistic(accountId, amount, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const row = await db.query(
      "SELECT balance, version FROM account WHERE id = ?", [accountId]
    );
    if (row.balance < amount) {
      throw new Error("Không đủ số dư"); // lỗi nghiệp vụ — KHÔNG retry
    }
    const result = await db.query(
      "UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?",
      [row.balance - amount, accountId, row.version]
    );
    if (result.affectedRows === 1) return { success: true };
    await sleep(50 * Math.pow(2, attempt)); // backoff: 50ms, 100ms, 200ms...
  }
  throw new Error("Giao dịch thất bại do tranh chấp, vui lòng thử lại sau");
}

Dừng retry khi:

  • Đã chạm giới hạn số lần thử (thường 3–5 lần) — row đang bị tranh chấp quá nặng, retry thêm chỉ tốn tài nguyên; nên trả lỗi hoặc chuyển sang queue/pessimistic lock cho riêng row đó.
  • Fail vì lý do nghiệp vụ (không đủ số dư) — không phải do conflict version, retry không giải quyết được gì.
  • Version nhảy bất thường liên tục — nên log điều tra thay vì retry mù.

1.8 — Deadlock: khi nào xảy ra, ví dụ cụ thể

Deadlock xảy ra khi 2 (hoặc nhiều) transaction cùng giữ lock của nhau và cùng đợi lock mà đối phương đang giữ — tạo thành vòng chờ khép kín, kẹt vĩnh viễn nếu DB không can thiệp.

Ví dụ: account id=1 có 10tr, account id=2 có 5tr. Cùng lúc có 2 giao dịch chuyển tiền ngược chiều nhau:

Transaction A — chuyển 1tr từ account 1 → 2
BEGIN;

-- Bước 1: lock account 1 trước
SELECT * FROM account WHERE id=1 FOR UPDATE;   -- A LOCK được row 1

-- Bước 2: cần lock thêm account 2 để cộng tiền
UPDATE account SET balance = balance + 1000000 WHERE id=2;
-- A phải CHỜ vì row 2 đang bị B giữ lock ...
Transaction B — chuyển 500k từ account 2 → 1 (chạy gần như cùng lúc)
BEGIN;

-- Bước 1: lock account 2 trước
SELECT * FROM account WHERE id=2 FOR UPDATE;   -- B LOCK được row 2

-- Bước 2: cần lock thêm account 1 để trừ tiền
UPDATE account SET balance = balance - 500000 WHERE id=1;
-- B phải CHỜ vì row 1 đang bị A giữ lock ...

-- KẸT CỨNG: A đợi B nhả row 2, B đợi A nhả row 1 → DEADLOCK

DB sẽ tự phát hiện vòng chờ khép kín này (deadlock detector chạy ngầm) và chủ động huỷ 1 trong 2 transaction, trả lỗi kiểu:

ERROR 1213: Deadlock found when trying to get lock; try restarting transaction

Transaction bị huỷ phải tự rollback và retry lại từ đầu ở tầng application. Transaction còn lại tiếp tục chạy bình thường.

A
Chuyển 1tr từ account 1 → 2. Lock account 1 trước (FOR UPDATE) — thành công.
B
Chuyển 500k từ account 2 → 1. Lock account 2 trước (FOR UPDATE) — thành công.
A
Cần lock thêm account 2 để cộng tiền → BỊ CHẶN vì B đang giữ.
B
Cần lock thêm account 1 để trừ tiền → BỊ CHẶN vì A đang giữ.
⛔
A đợi B, B đợi A → DEADLOCK. DB tự phát hiện và huỷ 1 trong 2 transaction.

Cách tránh: luôn lock các row theo một thứ tự cố định (ví dụ luôn theo id tăng dần), bất kể chiều nghiệp vụ của giao dịch là gì — để không bao giờ có 2 transaction giữ 2 row theo thứ tự ngược nhau.

Cả A và B đều lock account có id NHỎ HƠN trước, bất kể chiều chuyển tiền
-- app luôn tính: min_id = LEAST(from_id, to_id), max_id = GREATEST(from_id, to_id)
BEGIN;
SELECT * FROM account WHERE id = 1 FOR UPDATE;  -- luôn lock id nhỏ hơn trước
SELECT * FROM account WHERE id = 2 FOR UPDATE;  -- rồi mới lock id lớn hơn
-- ... thực hiện UPDATE cả 2 ...
COMMIT;

Dù A chuyển 1→2 hay B chuyển 2→1, cả 2 đều phải lock row id=1 trước tiên. Nếu A đã lock được row 1, B sẽ phải đợi ngay từ bước đầu — không xảy ra tình huống A giữ 1 chờ 2, B giữ 2 chờ 1 cùng lúc. B chỉ đơn giản đứng đợi ở hàng, không có vòng lặp khép kín.

Bổ sung thêm: giữ transaction càng ngắn càng tốt, set lock timeout (ví dụ innodb_lock_wait_timeout) để tránh treo vô hạn nếu deadlock detector chậm phát hiện, và ưu tiên atomic UPDATE thay vì nhiều câu lệnh giữ lock khi logic cho phép.

1.9 — Hiểu lầm thường gặp: Stored Procedure có tự tránh được race condition không?

✕ KHÔNG

Chuyển logic vào stored procedure không tự động giải quyết race condition. Vấn đề nằm ở việc có khoảng hở giữa đọc và ghi hay không — không liên quan tới việc code chạy ở tầng application hay bên trong DB. "Không có application nữa" không đồng nghĩa với "không có concurrency nữa": concurrency ở đây là 2 session/connection khác nhau gọi vào DB, không liên quan gì tới việc logic nằm ở app hay ở procedure.

Vẫn SAI dù nằm trong stored procedure, vì thiếu FOR UPDATE
CREATE PROCEDURE withdraw(IN acc_id INT, IN amount DECIMAL)
BEGIN
  DECLARE current_balance DECIMAL;
  -- Bước 1: đọc — PLAIN SELECT, không lock
  SELECT balance INTO current_balance FROM account WHERE id = acc_id;

  -- Bước 2: tính toán bên trong procedure (vẫn là "tính rồi mới ghi")
  IF current_balance >= amount THEN
    SET current_balance = current_balance - amount;
    -- Bước 3: ghi giá trị đã tính
    UPDATE account SET balance = current_balance WHERE id = acc_id;
  END IF;
END;

Kịch bản 2 session gọi gần như đồng thời:

A
SELECT balance INTO ... → đọc 10tr
B
SELECT balance INTO ... → CŨNG đọc 10tr (A chưa UPDATE, chưa commit → chưa đổi gì trong DB, B đọc thoải mái)
A
current_balance = 10tr - 6tr = 4tr → UPDATE balance = 4tr
B
current_balance = 10tr - 6tr = 4tr → UPDATE balance = 4tr (ghi đè, không biết gì về A)

Cả 2 session đều trừ thành công, balance cuối cùng là 4tr thay vì phải là -2tr (báo lỗi) hoặc chỉ 1 trong 2 thành công — y hệt lỗi race condition ở tầng app, vì bản chất vấn đề là plain SELECT không tạo lock, bất kể SELECT đó được gọi từ app hay từ trong procedure.

Cách sửa #1 — dùng FOR UPDATE để lock ngay khi đọc

CREATE PROCEDURE withdraw(IN acc_id INT, IN amount DECIMAL)
BEGIN
    DECLARE current_balance DECIMAL;

    START TRANSACTION;

    -- Dùng FOR UPDATE để LOCK row ngay khi đọc
    SELECT balance INTO current_balance FROM account WHERE id = acc_id FOR UPDATE;
    -- Session B gọi cùng lúc sẽ bị BLOCK ở đúng dòng này cho tới khi A COMMIT

    IF current_balance >= amount THEN
        UPDATE account SET balance = balance - amount WHERE id = acc_id;
        COMMIT;
    ELSE
        ROLLBACK;
    END IF;
END;

Cách sửa #2 — atomic UPDATE ngay trong procedure (gọn nhất)

CREATE PROCEDURE withdraw(IN acc_id INT, IN amount DECIMAL, OUT success BOOLEAN)
BEGIN
    UPDATE account SET balance = balance - amount
    WHERE id = acc_id AND balance >= amount;

    SET success = (ROW_COUNT() > 0);
END;

Cách 2 là tốt nhất — gọn, không cần transaction tường minh, không cần FOR UPDATE, vì cả đọc-check-ghi nằm trong 1 câu UPDATE atomic, đúng nguyên tắc y hệt mục 1.2. Nguyên tắc không đổi dù logic nằm ở app hay ở DB: muốn an toàn thực sự phải loại bỏ khoảng hở giữa đọc và ghi, chứ không phải chuyển chỗ chạy code.

Trả lời mẫu khi phỏng vấn

"Chuyển logic vào stored procedure không tự động giải quyết race condition, vì vấn đề nằm ở việc có tồn tại khoảng hở giữa đọc và ghi hay không — chứ không phải code chạy ở đâu. Nếu trong procedure vẫn viết kiểu SELECT rồi tính rồi UPDATE mà không lock, thì 2 session gọi procedure đó cùng lúc vẫn interleave với nhau y hệt race condition ở tầng app. Muốn an toàn thực sự, procedure vẫn phải dùng SELECT FOR UPDATE hoặc atomic UPDATE với điều kiện, đúng nguyên tắc y hệt như viết ở application."
