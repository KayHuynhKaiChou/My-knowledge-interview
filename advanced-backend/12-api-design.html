"Thiết kế API sao cho đúng chuẩn — REST, GraphQL, versioning, idempotent method là gì?"

12.1 — REST vs GraphQL vs gRPC — khi nào chọn cái nào

RESTGraphQLgRPC
Cách hoạt độngNhiều endpoint cố định, mỗi endpoint trả về 1 cấu trúc dữ liệu định sẵn1 endpoint duy nhất, client tự chọn chính xác field nào cần lấyGiao tiếp nhị phân (Protocol Buffers), tốc độ cao, định nghĩa contract rõ ràng qua file .proto
Ưu điểmĐơn giản, dễ cache (HTTP cache chuẩn), dễ debug (đọc được bằng mắt), hệ sinh thái tool lớnTránh over-fetching/under-fetching — FE không phải gọi nhiều lần hay nhận dư field không cầnNhanh hơn REST/GraphQL nhiều lần (nhị phân, HTTP/2), phù hợp giao tiếp nội bộ tốc độ cao

12.2 — Idempotent HTTP methods — method nào được phép gọi lại nhiều lần an toàn

"Idempotent" ở đây nghĩa là: gọi 1 lần hay gọi lại nhiều lần với cùng 1 request, kết quả cuối cùng trên server vẫn giống nhau — không tạo thêm tác dụng phụ nếu gọi lặp. Đây là khái niệm liên hệ trực tiếp với idempotency key đã học ở Câu 2, nhưng ở đây là tính chất mặc định của từng HTTP method theo chuẩn, không cần thêm cơ chế gì.

MethodIdempotent?Ý nghĩa
GETCóChỉ đọc dữ liệu, gọi bao nhiêu lần cũng không thay đổi gì trên server
PUTCóGhi đè toàn bộ resource bằng đúng dữ liệu gửi lên — gọi lại nhiều lần, resource vẫn ở đúng trạng thái đó, không đổi thêm
DELETECóXoá 1 resource — gọi lại lần 2 dù resource đã bị xoá từ lần 1, kết quả cuối cùng vẫn là "resource không tồn tại", không gây lỗi thêm
PATCHTuỳ cách viếtNếu patch kiểu "set field X = giá trị Y" thì idempotent; nếu patch kiểu "tăng field X thêm 1" thì KHÔNG idempotent (gọi 2 lần sẽ tăng 2 lần)
POSTKhôngThường dùng để tạo mới resource — gọi lại nhiều lần sẽ tạo ra nhiều resource trùng lặp (chính là bài toán double-submit ở Câu 2, cần idempotency key để bù đắp cho việc POST vốn dĩ không idempotent)

Ý nghĩa thực tế: vì POST không idempotent theo bản chất, nên với các API tạo giao dịch quan trọng (đặt hàng, thanh toán) luôn cần bổ sung thêm idempotency key ở tầng ứng dụng (Câu 2) để bù đắp cho tính chất này — đây là lý do 2 kiến thức này luôn đi kèm nhau khi phỏng vấn.

12.3 — API Versioning — vì sao cần và các cách phổ biến

Khi API đã có client đang dùng (mobile app cũ chưa update, đối tác đã tích hợp), không thể tự ý đổi cấu trúc response hay behavior của API cũ — sẽ làm hỏng những client đang phụ thuộc vào nó. Versioning cho phép vừa giữ API cũ hoạt động, vừa phát triển API mới song song.

Cách versioningVí dụƯu / nhược
URI Path/v1/orders, /v2/ordersDễ thấy, dễ debug, dễ route ở Gateway — cách phổ biến nhất
HeaderAccept: application/vnd.company.v2+jsonURL sạch hơn nhưng khó test nhanh bằng trình duyệt, dễ bị quên set header
Query Param/orders?version=2Dễ làm nhưng dễ bị quên truyền, không phải chuẩn phổ biến

Khi nào cần bump version: chỉ cần khi có breaking change — đổi cấu trúc response, xoá field cũ, đổi ý nghĩa 1 field. Thêm field mới (optional) hoặc thêm endpoint mới thường không cần bump version, vì không phá vỡ client cũ đang dùng.

12.4 — Chuẩn hoá format response và lỗi trong dự án

Một API design tốt cần format response nhất quán giữa mọi endpoint, để FE xử lý dễ dàng mà không cần biết trước cấu trúc riêng của từng API.

// Response thành công — bọc trong 1 envelope chung
{
  "success": true,
  "data": { "id": 1, "name": "..." },
  "meta": { "page": 1, "totalPages": 10 }   // nếu có phân trang
}

// Response lỗi — format thống nhất cho MỌI lỗi, dù lỗi 400, 404, hay 500
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_BALANCE",     // mã lỗi máy đọc được, để FE switch-case xử lý
    "message": "Số dư không đủ để thực hiện giao dịch",  // message người đọc được
    "details": { "currentBalance": 2000000, "requiredAmount": 5000000 }
  }
}

Lợi ích của format lỗi có code riêng biệt: FE có thể xử lý logic khác nhau dựa vào code (ví dụ hiện popup nạp tiền khi gặp INSUFFICIENT_BALANCE) mà không cần so sánh chuỗi message (dễ vỡ nếu đổi ngôn ngữ hiển thị hoặc chỉnh sửa câu chữ).

Trả lời mẫu khi phỏng vấn

"Em chọn REST cho hầu hết API CRUD thông thường vì dễ tích hợp và cache, chỉ cân nhắc GraphQL khi FE cần linh hoạt lấy dữ liệu từ nhiều nguồn khác nhau, và gRPC cho giao tiếp nội bộ giữa các service cần tốc độ cao. Về versioning em dùng URI path vì dễ debug và route ở Gateway, chỉ bump version khi có breaking change thật sự. Em luôn chuẩn hoá format response và lỗi thống nhất giữa các endpoint, đặc biệt lỗi luôn có mã code riêng để FE xử lý logic theo code thay vì so sánh message, tránh vỡ khi đổi ngôn ngữ hiển thị."
