6 Câu hỏi ứng dụng thường gặp

"Bảng transaction log hàng chục triệu row, query theo account_id ngày càng chậm — tối ưu sao?"

6.1 — Composite Index: gộp nhiều cột vào 1 index

Composite index (compound index) là gộp 2 hoặc nhiều cột vào chung 1 index, thay vì tạo riêng từng index cho từng cột.

CREATE TABLE transactions (
  id BIGINT PRIMARY KEY,
  account_id INT,
  created_at TIMESTAMP,
  amount DECIMAL,
  status VARCHAR(20)
);

-- Query thường gặp: lấy lịch sử giao dịch của 1 account, mới nhất trước
SELECT * FROM transactions
WHERE account_id = 123
ORDER BY created_at DESC
LIMIT 20;

Không có index → DB phải quét toàn bộ hàng chục triệu row để tìm account_id = 123, rồi mới sort — cực chậm.

Composite index đúng
CREATE INDEX idx_account_created ON transactions (account_id, created_at);

Thứ tự cột trong composite index rất quan trọng — index này giúp nhanh khi:

WHERE account_id = 123                                 -- ✅ dùng được index (cột đầu)
WHERE account_id = 123 AND created_at > '2026-01-01'   -- ✅ dùng được cả 2 cột
WHERE account_id = 123 ORDER BY created_at             -- ✅ index đã sort sẵn theo created_at
                                                        --    trong phạm vi account_id đó, khỏi sort lại

Nhưng không giúp gì nếu query chỉ lọc theo cột thứ 2 mà bỏ qua cột đầu:

WHERE created_at > '2026-01-01'   -- ❌ không tận dụng được index này,
                                  --    vì index được sắp xếp theo account_id trước

Nguyên tắc: composite index hoạt động giống mục lục sách theo "Chương → Trang" — muốn tra nhanh trang 50 của chương 3, phải biết chương trước; chỉ có "trang 50" mà không biết chương nào thì mục lục này vô dụng.

6.2 — Partition: chia nhỏ 1 bảng lớn thành nhiều "bảng con" vật lý

Partition không phải là index — nó là cách vật lý chia dữ liệu của 1 bảng ra thành nhiều phần riêng dựa theo 1 cột (thường là thời gian), nhưng vẫn cho phép query như thể đó là 1 bảng duy nhất.

-- Partition bảng transactions theo THÁNG dựa vào created_at
CREATE TABLE transactions (
  id BIGINT,
  account_id INT,
  created_at TIMESTAMP,
  amount DECIMAL
) PARTITION BY RANGE (created_at) (
  PARTITION p_2026_06 VALUES LESS THAN ('2026-07-01'),
  PARTITION p_2026_07 VALUES LESS THAN ('2026-08-01'),
  PARTITION p_2026_08 VALUES LESS THAN ('2026-09-01')
);

Về mặt vật lý, dữ liệu tháng 6 nằm ở 1 file/phân vùng riêng, tháng 7 riêng, tháng 8 riêng — dù bạn vẫn SELECT * FROM transactions như 1 bảng bình thường.

-- Query này chỉ cần quét PHÂN VÙNG tháng 8, bỏ qua hoàn toàn tháng 6, 7
SELECT * FROM transactions
WHERE created_at >= '2026-08-01' AND created_at < '2026-08-31';

DB engine biết ngay chỉ cần đọc p_2026_08, không cần động vào 2 phân vùng kia — gọi là partition pruning. Khác index ở chỗ: index giúp tìm nhanh trong 1 khối dữ liệu, còn partition giúp loại bỏ hẳn cả khối dữ liệu không liên quan trước khi tìm kiếm — hiệu quả rất lớn khi bảng có hàng chục/trăm triệu row trải dài nhiều năm.

6.3 — Archive dữ liệu cũ: di chuyển dữ liệu ít dùng ra khỏi bảng chính

Dữ liệu cũ (ví dụ giao dịch từ 2 năm trước) gần như không ai còn query hàng ngày nữa — nhưng vẫn nằm trong bảng chính, làm bảng phình to, làm chậm cả index lẫn query của dữ liệu mới (index cũng phải lớn theo, backup cũng lâu hơn).

-- Bước 1: copy dữ liệu cũ (>2 năm) sang bảng archive (hoặc storage khác như S3)
INSERT INTO transactions_archive
SELECT * FROM transactions
WHERE created_at < '2024-01-01';

-- Bước 2: xoá khỏi bảng chính sau khi archive thành công
DELETE FROM transactions WHERE created_at < '2024-01-01';

Kết quả: bảng transactions (bảng chính, phục vụ giao dịch hàng ngày) giờ chỉ chứa dữ liệu gần đây, nhỏ gọn, index nhanh, insert/update mượt hơn. Cần tra lịch sử cũ (hiếm khi, thường là báo cáo/audit) thì query sang transactions_archive riêng — chấp nhận chậm hơn vì không phải hot path.

Kết hợp với partition: thay vì DELETE từng dòng (chậm với bảng lớn), nếu bảng đã partition theo tháng, archive chỉ đơn giản là "gỡ hẳn 1 partition ra" — cực nhanh, không cần quét từng row.

6.4 — N+1 Query: lỗi rất hay gặp khi dùng ORM

Thay vì lấy hết dữ liệu cần trong 1–2 câu query, code chạy 1 query lấy danh sách (N record), rồi thêm N query riêng lẻ để lấy dữ liệu liên quan cho từng record — tổng cộng N+1 lần gọi DB.

Sai — N+1 query
// Bước 1: 1 query lấy 20 đơn hàng
const orders = await db.query("SELECT * FROM orders LIMIT 20");   // → 1 query

// Bước 2: LẶP qua từng order, mỗi lần lại query riêng để lấy tên sản phẩm
for (const order of orders) {
  const product = await db.query(
    "SELECT name FROM products WHERE id = ?", [order.product_id]
  );
  order.productName = product.name;
}
// → thêm 20 query nữa, mỗi order 1 lần

// TỔNG: 1 (lấy orders) + 20 (lấy product từng cái) = 21 query cho có 20 record

Với 20 record chưa thấy rõ, nhưng nếu trang danh sách có 1000 đơn hàng → 1001 lần gọi DB cho 1 lần load trang, cực chậm dù mỗi query riêng lẻ đều nhanh.

Đúng — JOIN 1 lần
SELECT orders.*, products.name AS product_name
FROM orders
JOIN products ON products.id = orders.product_id
LIMIT 20;
-- CHỈ 1 query duy nhất, lấy hết dữ liệu cần trong 1 lần
Hoặc batch IN(...) nếu không tiện JOIN trực tiếp
const orders = await db.query("SELECT * FROM orders LIMIT 20");     // query 1
const productIds = orders.map(o => o.product_id);                    // gom hết id lại
const products = await db.query(
  "SELECT * FROM products WHERE id IN (?)", [productIds]
);                                                                     // query 2 — LẤY HẾT 1 LẦN
// rồi map product vào từng order ở tầng app (không cần query DB thêm nữa)

Chỉ còn 2 query cố định, dù danh sách orders có 20 hay 1000 record — điểm khác biệt cốt lõi: N+1 tăng tuyến tính theo số record, còn cách sửa giữ nguyên số query bất kể data lớn cỡ nào. Nhiều ORM có sẵn cú pháp để tự động hoá việc này (TypeORM: relations, Prisma: include, Sequelize: include) — bản chất bên dưới cũng chuyển thành JOIN hoặc batch IN như trên.

Phát hiện N+1 qua log SQL hoặc APM (New Relic, Datadog) đếm số query/request.

6.5 — Cache balance trong Redis — có nên dùng để check trước khi trừ?

✕ Không dùng cache để check trước khi trừ tiền

Chỉ nên cache cho mục đích đọc hiển thị (dashboard). Trừ tiền luôn phải đọc từ DB (nguồn sự thật) với lock đúng cách, vì cache có độ trễ đồng bộ → dùng cache để check số dư trước khi trừ có thể trừ vượt quá thực tế.
