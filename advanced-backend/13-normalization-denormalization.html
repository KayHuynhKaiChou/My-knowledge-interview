13 Câu hỏi ứng dụng thường gặp

"Normalization và Denormalization trong thiết kế DB là gì, khi nào chọn cái nào?"

13.1 — Normalization (chuẩn hoá) là gì

Normalization là quá trình tổ chức dữ liệu sao cho mỗi thông tin chỉ được lưu đúng 1 lần, ở đúng 1 chỗ — tách dữ liệu ra thành nhiều bảng nhỏ, liên kết với nhau qua khoá ngoại (foreign key), để tránh dư thừa dữ liệu (redundancy) và tránh bất thường khi cập nhật (update anomaly).

Ví dụ vấn đề khi KHÔNG chuẩn hoá

-- Bảng orders KHÔNG chuẩn hoá — nhồi hết thông tin khách hàng vào từng dòng đơn hàng
CREATE TABLE orders (
  id INT,
  customer_name VARCHAR(255),
  customer_email VARCHAR(255),
  product_name VARCHAR(255),
  product_price DECIMAL,
  quantity INT
);

-- id | customer_name | customer_email | product_name | product_price | quantity
-- 1  | Nguyen Van A   | a@gmail.com     | Áo thun      | 150000        | 2
-- 2  | Nguyen Van A   | a@gmail.com     | Quần jean    | 350000        | 1
-- 3  | Nguyen Van A   | a@gmail.com     | Giày         | 500000        | 1

Thông tin "Nguyen Van A" và email bị lặp lại 3 lần. Nếu khách đổi email, phải UPDATE cả 3 dòng — quên 1 dòng là dữ liệu mâu thuẫn (dòng thì email cũ, dòng thì email mới) — đây là "update anomaly".

Sau khi chuẩn hoá — tách bảng, liên kết qua khoá ngoại

CREATE TABLE customers (
  id INT PRIMARY KEY, name VARCHAR(255), email VARCHAR(255)
);
CREATE TABLE products (
  id INT PRIMARY KEY, name VARCHAR(255), price DECIMAL
);
CREATE TABLE orders (
  id INT PRIMARY KEY, customer_id INT REFERENCES customers(id)
);
CREATE TABLE order_items (
  id INT PRIMARY KEY, order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id), quantity INT
);

Thông tin khách hàng giờ chỉ tồn tại đúng 1 dòng duy nhất. Đổi email chỉ cần UPDATE customers ... WHERE id = 1 — 1 lần duy nhất, mọi đơn hàng liên kết tới customer đó tự động "thấy" email mới khi join.

Cái giá phải trả: phải JOIN nhiều bảng khi đọc

SELECT o.id, c.name, c.email, p.name AS product_name, oi.quantity, p.price
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id = 1;

Càng nhiều bảng phải JOIN, query càng phức tạp và có thể chậm hơn khi data lớn — đây chính là điểm mà Denormalization can thiệp vào.

13.2 — Denormalization (phi chuẩn hoá) là gì

Denormalization là chủ động chấp nhận dư thừa dữ liệu 1 phần (đi ngược nguyên tắc chuẩn hoá) để đổi lấy tốc độ đọc nhanh hơn, giảm số lượng JOIN cần thiết — thường áp dụng sau khi đã chuẩn hoá đúng chuẩn, nhưng đo được rằng JOIN đang là nút thắt hiệu năng thực sự.

Ví dụ 1 — snapshot giá tại thời điểm đặt hàng

CREATE TABLE order_items (
  id INT PRIMARY KEY,
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),
  product_name VARCHAR(255),   -- DƯ THỪA có chủ đích — copy lại từ bảng products
  product_price DECIMAL,        -- DƯ THỪA có chủ đích — giá TẠI THỜI ĐIỂM đặt hàng
  quantity INT
);

Đây không chỉ là tối ưu tốc độ — nó giải quyết đúng 1 bài toán nghiệp vụ: nếu sau này shop đổi giá sản phẩm, đơn hàng cũ vẫn phải hiển thị đúng giá tại thời điểm khách đã mua, không phải giá hiện tại — nếu chỉ JOIN sang bảng products để lấy giá, hoá đơn cũ sẽ tự động đổi sai theo giá mới, gây sai lệch tài chính nghiêm trọng. Denormalize product_price vào ngay order_items chính là cách "chụp lại ảnh chớp nhoáng" (snapshot) dữ liệu tại đúng thời điểm giao dịch.

Ví dụ 2 — đếm sẵn thay vì tính lại mỗi lần

-- Thay vì mỗi lần hiển thị bài viết phải COUNT(*) từ bảng comments (chậm nếu triệu comment)
SELECT COUNT(*) FROM comments WHERE post_id = 5;

-- Denormalize: thêm cột đếm sẵn ngay trên bảng posts
ALTER TABLE posts ADD COLUMN comment_count INT DEFAULT 0;

-- Đọc bài viết giờ chỉ cần 1 câu, không cần COUNT nữa
SELECT title, comment_count FROM posts WHERE id = 5;

Đánh đổi: giờ có 2 chỗ lưu cùng 1 thông tin (số comment thật trong bảng comments, và số đếm sẵn trong posts) — nếu code có bug quên tăng comment_count khi thêm comment, 2 số này sẽ lệch nhau, y hệt tinh thần "lệch cache-DB" đã học ở Câu 7, chỉ khác là đây là lệch giữa 2 bảng trong cùng 1 DB.

13.3 — Đảm bảo đồng bộ khi ghi denormalized data: Transaction hoặc Trigger

2 câu lệnh INSERT comment và UPDATE comment_count là 2 câu lệnh SQL tách biệt. Nếu chỉ viết tuần tự mà không có gì ràng buộc: INSERT chạy thành công, nhưng server crash/lỗi trước khi kịp chạy UPDATE — kết quả là comments có dữ liệu mới nhưng posts.comment_count không tăng theo, gây lệch.

Cách 1 — Transaction: gói 2 câu lệnh thành 1 khối "cùng sống cùng chết"

BEGIN;
INSERT INTO comments (post_id, content) VALUES (5, 'Hay quá');
UPDATE posts SET comment_count = comment_count + 1 WHERE id = 5;
COMMIT;
-- Nếu có lỗi ở bất kỳ dòng nào trước COMMIT → ROLLBACK toàn bộ,
-- không có chuyện chỉ 1 trong 2 câu lệnh thành công

Áp dụng đúng nguyên lý ACID đã dùng xuyên suốt từ mục 1.2 — đảm bảo INSERT và UPDATE luôn cùng thành công hoặc cùng thất bại.

Cách 2 — Trigger: để DB tự động làm, không phụ thuộc code application

CREATE TRIGGER trg_increment_comment_count
AFTER INSERT ON comments
FOR EACH ROW
BEGIN
  UPDATE posts SET comment_count = comment_count + 1 WHERE id = NEW.post_id;
END;

Mỗi khi có 1 dòng mới được INSERT vào bảng comments, DB tự động chạy thêm câu UPDATE để tăng comment_count, không cần lập trình viên tự viết thêm dòng code ở tầng application. Dù ai gọi INSERT INTO comments từ đâu — API, script backfill, công cụ quản trị DB — trigger vẫn tự chạy, đảm bảo đồng bộ mà không phụ thuộc việc lập trình viên có nhớ viết đúng ở mọi nơi hay không.

Trả lời mẫu khi phỏng vấn

"Em thiết kế theo chuẩn hoá trước để đảm bảo tính nhất quán, tránh dư thừa và mâu thuẫn dữ liệu khi update — đặc biệt với dữ liệu giao dịch quan trọng. Chỉ khi đã đo được JOIN đang là nút thắt hiệu năng thực sự, hoặc có yêu cầu nghiệp vụ cần lưu lại snapshot dữ liệu tại 1 thời điểm như giá sản phẩm lúc đặt hàng, em mới cân nhắc denormalize có chủ đích — và luôn đảm bảo đồng bộ đúng bằng transaction hoặc trigger, vì denormalize tạo ra 2 nơi lưu cùng 1 thông tin, nếu ghi không đồng bộ sẽ dẫn tới dữ liệu lệch nhau giữa các bảng."
